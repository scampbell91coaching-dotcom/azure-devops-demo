# V7.3 nutrition macro prescription domain

## Outcome

V7.3 now has a typed, migration-free foundation for coach-authored macro
prescriptions. `portal.services.nutrition_prescriptions` is deliberately pure
Python: it has no Flask, SQLAlchemy, template, or database dependency.

A macro prescription is the source of truth for what an athlete has been asked
to consume. It is not a nutrition diary and does not calculate adherence.

## Existing concepts inspected

The current application has three observation paths:

| Existing concept | Meaning | Future relationship to prescriptions |
| --- | --- | --- |
| `NutritionCheckIn` | Athlete-reported weekly averages, wellbeing scores, and copied legacy targets | Keep averages and adherence as observations; resolve targets by check-in date instead of asking the athlete to copy them |
| `WeeklyCheckin` | Modular weekly observation with imported/manual averages | Keep actual intake, source, period, notes, and adherence separate |
| `DailyNutrition` | Provider-imported daily intake and bodyweight | Actual intake only; compare with a resolved prescription in a separate reporting service |

The athlete nutrition form currently asks for both targets and actual averages.
The athlete and coach dashboards then render those stored values together. Those
routes and templates are unchanged in this migration-free slice. MyFitnessPal
imports already use the useful core names `calories`, `protein_g`,
`carbohydrate_g`, `fat_g`, and optional `fibre_g`; the new target value object
reuses that vocabulary.

## Domain model

`MacroTargets` contains required calories, protein, carbohydrate, and fat, plus
optional fibre. Values use integer kcal/grams and the same broad input safety
bounds as the established nutrition check-in form. The domain intentionally
does not force calories to equal `4P + 4C + 9F`; food labels, fibre, alcohol, and
rounding make that an unreliable invariant.

`MacroPrescription` contains:

- a stable prescription ID and athlete ID;
- default daily targets;
- optional training-day and rest-day target overrides;
- inclusive `effective_from` and optional `effective_until` dates;
- optional meal count and coach notes;
- mandatory provenance.

The daily target is always present. A missing requested variant falls back to
the daily target, which supports simple prescriptions without inventing values.
Meal count is optional guidance, not a meal plan.

`PrescriptionProvenance` records the actor ID, actor role, source, optional
source reference, and a timezone-aware recorded timestamp. It supports audit
and later revisions without treating generated recommendations as coach
approval. The default source is `coach_authored`.

## Service behavior

`MacroPrescriptionService.assign` rejects duplicate IDs and overlapping
inclusive effective periods for the same athlete. Adjacent prescriptions are
valid when the earlier one ends the day before the later one starts.

`resolve(athlete_id, date, day_type)` finds the prescription effective on that
date and returns a `ResolvedMacroTargets` projection carrying targets, context,
notes, meal count, and provenance. Gaps return `None`. Ambiguous repository data
raises `PrescriptionConflictError` rather than silently choosing a source of
truth.

## Persistence seam

`MacroPrescriptionRepository` is a protocol with two operations:

```python
list_for_athlete(athlete_id) -> Sequence[MacroPrescription]
add(prescription) -> None
```

The included in-memory adapter supports tests and configuration-backed trials.
A future SQLAlchemy adapter should map records to domain objects at its boundary
and enforce athlete/effective-period conflicts transactionally. Likely future
storage needs are a prescription header, default/variant target rows (or typed
columns), an effective-period constraint, provenance fields, and revision/audit
metadata. That design requires a separately reviewed migration and is not part
of V7.3 Agent B work.

Updates should be append/revise operations that close an old period and create a
new prescription, preserving the historical target for prior check-ins. Do not
overwrite a historical prescription in place. Repository implementations should
also scope every read and write by athlete and authorization context.

## Coach and athlete UX seams

Coach UX can submit a command DTO that is converted into `MacroTargets`,
`PrescriptionProvenance`, and `MacroPrescription`, then passed to `assign`.
Useful form behaviors are:

- default daily targets first, with an explicit training/rest variant toggle;
- effective start and optional end dates with overlap errors shown inline;
- optional fibre, meal count, and notes;
- a review step showing author and effective dates;
- history as immutable dated revisions rather than one editable current row.

Athlete UX should call `resolve` for the viewed date, label the result as a coach
target, show whether daily/training/rest targets apply, and show the effective
date. Check-in forms should display resolved targets read-only and collect only
actual intake and self-reported adherence.

A future comparison/adherence service may accept a resolved prescription and
observed `DailyNutrition`/check-in values as separate inputs. It should define
period coverage, missing data, tolerance, and training-day classification
explicitly. No such calculations belong in the prescription aggregate.

## Explicit non-goals

This foundation does not provide medical diets, diagnostic rules, autonomous AI
dieting, food logging, a food database, meal plans, micronutrient prescriptions,
or adherence scoring. It does not alter routes, templates, database schemas,
migrations, or production configuration.

## Test coverage

Focused unit tests cover daily resolution, training/rest variants and fallback,
inclusive effective dates, gaps, macro bounds, metadata validation, overlap and
duplicate rejection, adjacent periods, athlete isolation, ambiguous persisted
data, and the absence of actual-intake/adherence fields.
