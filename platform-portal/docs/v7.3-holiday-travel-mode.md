# V7.3 Holiday / Travel Mode

## Decision

Holiday/travel is a dedicated, date-bounded domain entity. Its effective value is
consumed as a scheduling constraint and may contribute athlete-state context, but
it is neither a generic athlete-state fact nor a check-in note.

This split matters: an event has lifecycle, dates, provenance, approval and
overlap rules; a scheduling constraint is the derived answer used by Block
Factory and session presentation. Check-ins may mention travel and athlete-state
signals may explain readiness, but neither should create or alter a holiday.

The schema-independent contract lives in
`portal/services/holiday_mode.py`. It has no Flask, ORM or database dependency.

## Existing platform fit

- Athlete state is auditable, superseding facts plus observations, constraints,
  calculated signals, recommendations and coach overrides. It is not a calendar.
- Programming is Block → ordered Week → ordered Session → prescriptions/lift
  slots. Blocks have a status, but weeks/sessions currently have positions and
  day labels rather than calendar dates.
- Completed session logs snapshot prescription details, preserving history.
- Weekly check-ins are dated reports of adherence/recovery/nutrition. They are
  evidence, not forward scheduling.
- Exercise Library already exposes equipment options, compatibility/constraint
  tags and warm-up/accessory suitability. Those fields can support exact-match
  filtering once their equipment vocabulary is normalised.

The missing prerequisite for automatic calendar application is an explicit
scheduled date for a session (or an unambiguous block/week anchor plus weekday).
Until then, callers must provide `SessionContext.scheduled_on`; no date should be
inferred from a week position or free-text day label.

## Domain rules

Dates are inclusive local calendar dates. Weekdays are integers Monday=0 through
Sunday=6. Cancelled events do not constrain scheduling. Two non-cancelled events
for the same athlete may not overlap, including touching on the same day. An API
adapter should return a conflict with both event IDs; it must not select one
silently.

`planned/active/completed/cancelled` is persisted workflow state. For display,
upcoming/active/past is derived from the requested local date; completed always
displays as past and cancelled as cancelled. A background job may advance
workflow state, but correct display must not depend on that job.

The effective return date is the explicit return-to-training date, otherwise the
day after `ends_on`. An explicit date must be later than the holiday. Re-entry is
a review boundary, not permission to rewrite the following programme.

Coach override is field-level, wins over athlete submission, and requires actor
and reason. Unset override fields retain the submitted value. Both layers must be
shown in audit history. Cancellation and approval are separate concerns: MVP can
represent approval by an audited coach override/decision, while the future schema
should persist approval explicitly.

### Deterministic training policy

| Effective availability | Conditions | Session result |
|---|---|---|
| none | intent must be pause | Hide assignment in the holiday view; label paused; retain original |
| reduced | unavailable weekday | Hide for that day; retain original |
| reduced | required equipment missing + substitute intent | Propose compatible substitute |
| reduced | required equipment missing + other intent | Coach review; never guess |
| reduced | day/equipment available | Propose reduced session |
| normal | equipment missing + substitute intent | Propose compatible substitute |
| normal | equipment missing + other intent | Coach review |
| normal | equipment available + substitute intent | Propose substitute |
| normal | equipment available | Present original with “training away” context |

An empty equipment set means no equipment, not unknown. A persistence/API layer
must model unknown separately (nullable input or an explicit `unknown` state)
before constructing the domain object. Required equipment is an exact canonical
tag set. A session is accessible only when every required tag is available.

Bodyweight and nutrition intent are informational in MVP. Holiday Mode must not
change macro targets. Any future macro recommendation is separately proposed,
explained and explicitly accepted.

## Block Factory and session presentation

Block Factory should accept holidays intersecting the proposed block calendar,
calculate per-session decisions, and show them in preview. For draft blocks it
may generate a separate holiday-compatible proposal or pause markers. Acceptance
creates a new auditable programme revision/snapshot.

For active/published programming, Holiday Mode is a presentation overlay:

1. retain the original session and prescription IDs/content;
2. show paused, reduced, substitute or coach-review state for the scheduled date;
3. let the coach accept a proposed alternative as a separately identified
   revision linked to the original;
4. keep completed logs and original programming readable forever; and
5. never auto-delete, move, overwrite or silently mark a session completed.

Accessory and warm-up candidate selection should add available equipment as a
required filter before ranking. If metadata is absent or no exact compatible
candidate exists, show coach review rather than invent compatibility. Main-lift
substitution follows the same rule. The policy result contains
`preserve_original=True` to make the non-destructive contract explicit.

On the return date, show a re-entry checkpoint with missed/paused sessions,
recent check-in context and options to resume, insert a coach-authored re-entry
session, or revise future programming. None is selected automatically.

## UX

Athlete flow: “Add time away” from dashboard/calendar; start/end; location and
time zone (optional); normal/reduced/none; available weekdays; equipment/gym
access; programming preference; optional bodyweight/nutrition intent and notes;
return date; review and submit. Show pending coach review, effective plan,
differences introduced by coach, cancel action, and a local-date summary.

Coach flow: upcoming-holidays queue (next 30 days), conflicts and unreviewed
submissions first; athlete/date/status filters; side-by-side submission and
effective override; affected session preview; approve as submitted or override
with mandatory reason. Athlete and coach views use the same policy result.

Warnings should distinguish “session paused”, “equipment incompatible”, “date
not scheduled”, and “coach review needed”. Do not imply an athlete skipped a
session merely because Holiday Mode hid it.

## Future persistence proposal (no migration in V7.3 foundation)

`athlete_holiday_periods`: UUID/id, athlete_id FK, starts_on, ends_on, location,
IANA time_zone, availability, programming_intent, available_days JSON/child rows,
equipment_tags JSON/child rows, bodyweight_intent, nutrition_intent, notes,
return_to_training_on, provenance, source_actor_id, status, submitted/created/
updated/cancelled timestamps, version. Constraints validate enums, end >= start,
return > end, and availability/intent consistency. Index athlete/date/status.
Prevent overlap transactionally (Postgres exclusion constraint on inclusive
daterange for non-cancelled rows, with service validation for portability).

`athlete_holiday_overrides`: id, holiday_id FK, nullable override fields, reason,
actor_id, created_at, revoked_at, version. Retain revisions rather than update in
place. `athlete_holiday_decisions`: holiday_id, approval status
(pending/approved/changes_requested), actor, reason, decided_at, version.

If equipment becomes relational, use `holiday_equipment` joined to a canonical
equipment taxonomy shared by Exercise Library. Store a programme proposal/link
table for holiday alternatives: holiday_id, original_session_id, proposed
session/revision ID, action, policy_version, status, actor and timestamps. Never
place substituted content over the original row.

All writes use optimistic version checks and an audit/outbox event. Authorisation
requires athlete-self scope or coach scope for that athlete. Store calendar dates
as dates; validate IANA time zone but do not convert date boundaries through UTC.

## MVP acceptance criteria

- Athlete or coach can describe every required event field through the typed
  contract; invalid dates, weekdays and no-training combinations are rejected.
- Upcoming, active, past and cancelled display state is deterministic for a
  supplied date, including both boundaries.
- Same-athlete overlaps are reported deterministically; cancelled and other-
  athlete events do not conflict.
- Coach overrides require actor/reason, apply per field, and win in policy output.
- No/reduced/normal and equipment-limited cases return the documented action.
- Inaccessible equipment never produces an unverified exercise suggestion.
- Return date defaults to end + 1 and rejects dates during the holiday.
- Every session decision preserves the original programming; published content,
  completed logs and macro targets are never silently mutated.
- Block Factory can consume decisions in preview without an ORM dependency;
  session UI can display the same decision and rationale.
- Tests cover overlap, temporal state, equipment, coach override, return date and
  no-training behavior.
- No migration or production/configuration change ships with this foundation.

## Deferred decisions

Canonical equipment taxonomy, approval SLA/notifications, recurrence, partial-day
travel, multiple time zones, programme calendar anchoring, and the exact re-entry
algorithm require product/data work. They must not be inferred in MVP.
