# V7.13 SaaS foundation audit

Status: design/audit only. This document describes the schema and access behaviour at
the V7.13 baseline. It does not authorize enabling multi-coach SaaS on the current
schema.

## Executive conclusion

The current portal is a secure-enough single-coach application boundary, not a tenant
boundary. Authentication distinguishes a global `coach` role from an athlete account.
`portal.auth._authorize_request` permits every authenticated coach to every non-public
endpoint. There is no tenant, organisation, coach-membership, or coach-athlete ownership
record. Most domain rows are rooted in `athletes`; programming children inherit that
root transitively. This gives good raw material for an additive migration, but it does
not isolate two coaches.

Do not onboard a second mutually untrusted coaching business until tenant membership,
tenant-scoped repositories, database constraints, and negative isolation tests are in
place. A second `coach` user today can enumerate, read, and mutate all athletes and all
coach-owned data.

## Current ownership graph

Arrows mean “has a database foreign key to”. `[global]` means intentionally shared or
operational data. `[orphan root]` means business data with no tenant/athlete owner.

```text
users (global identity; coach has no owner)
  -> athletes (only athlete-role users; unique users.athlete_id)

athletes (current de-facto ownership root)
  <- account_tokens (also -> users)
  <- athlete_checkin_settings
  <- weekly_checkins
  <- nutrition_checkins
  <- nutrition_provider_connections
  <- nutrition_import_jobs <- daily_nutrition (also has athlete_id)
  <- nutrition_macro_prescriptions (also -> author user)
  <- client_service_changes (also -> actor user)
  <- athlete_state_facts/signals/recommendations/overrides/constraint_flags
  <- coach_technical_observations
  <- external_coaching_reviews
  <- training_blocks <- training_weeks <- training_sessions
       <- programming_lift_slots <- exercise_prescriptions
       <- exercise_prescriptions
       <- warmup assignments/overrides/snapshots (also carry athlete_id)
  <- training_session_logs <- training_set_results
  <- programme_revisions (also -> block and author user)
  <- meal_plan_assignments (also -> publisher user; template_id is not an FK)
  <- meet_entries <- meet_lifts

meal_plan_templates -> users.coach_id (coach-owned, but repository reads are global)
warmup_protocols -> creator user (catalogue is globally readable)
exercises <- day_template_exercises -> day_templates                 [global catalogue]
meets                                                               [orphan root]
coaching_applications                                               [orphan root]
lead_captures                                                       [orphan root]
platform_snapshots                                                  [global operations]
```

Important integrity gaps already present inside the graph:

- A meet has no owner. Entries may combine athletes that would later belong to
  different tenants.
- `meal_plan_assignments.template_id` is indexed text, not a foreign key, so an
  assignment cannot prove that its template and athlete share an owner.
- Dual-root rows (`programme_revisions`, session logs, warmups, reviews, daily
  nutrition) can point to ancestors belonging to a different athlete. Existing FKs
  prove existence, not same-owner consistency.
- Actor columns point to users but cannot prove that the actor belongs to the record's
  tenant.
- Email and several catalogue keys are globally unique. That may be correct for login
  identity, but should not accidentally become the tenant lookup mechanism.

## Current authorization and single-coach assumptions

The exhaustive code-level assumption inventory is below. “Global” means no tenant
predicate exists because the schema cannot express one. Athlete-id filtering is useful
object ownership, but it is not coach/tenant isolation.

### Authentication boundary

- `portal/auth.py`: `UserRole` has only coach/athlete semantics. `_authorize_request`
  returns immediately for every coach. `_requested_athlete_id` protects athlete users
  only when the route variable is literally named `athlete_id`; it is not a general
  object authorization mechanism. `roles_required(COACH)` proves role, not ownership.
- `portal/models/user.py`: coach users must have `athlete_id IS NULL`; there is no
  membership, tenant, support, or platform-admin role.
- `portal/__init__.py`: all coach, operational, history, security and API blueprints
  share the same authenticated application boundary.

### Users, coaches, athletes and accounts

- `portal/athletes.py`: athlete list/create/detail, onboarding, services, invitations,
  resets, nutrition review and programme selection use global athlete lookup/listing.
- `portal/programming_routes/athletes.py`, `portal/programming_templates.py`,
  `portal/block_factory.py`, `portal/meet_day.py`, and `portal/meal_plan_delivery.py`
  populate selectors from all athletes.
- `portal/auth.py`: CLI user creation can attach an athlete user to any athlete; coach
  creation creates a globally privileged coach.
- `portal/services/account_lifecycle.py` and `portal/models/account_token.py`: tokens
  are athlete/user scoped but have no tenant context; a globally privileged coach may
  issue/revoke them through `portal/athletes.py`.

### Blocks, weeks, sessions and prescriptions

- `portal/programming_routes/{athletes,blocks,weeks,sessions,lift_slots,prescriptions,
  warmups}.py`: direct primary-key loads are trusted after global coach authorization.
- `portal/programming_pack2.py`, `portal/programming_engine.py`,
  `portal/programming_templates.py`, and `portal/block_factory.py`: direct block,
  session, prescription, recommendation and athlete loads have no tenant predicate.
- `portal/programming_services/{blocks,weeks,sessions,prescriptions,lift_slots,
  revisions,warmups}.py`: service contracts accept records/ids without an owner scope.
- Exercise, day-template and warmup-protocol catalogues are global. This is reasonable
  only if they remain platform-managed; coach-authored variants need tenant ownership.

### Check-ins, nutrition and meal plans

- `portal/checkins.py`: coach inbox lists every weekly check-in; detail/review uses a
  direct id. Athlete routes do correctly pair check-in id with the current athlete.
- `portal/athletes.py`: nutrition dashboard/check-in review is athlete-filtered but the
  selected athlete is globally loadable by a coach.
- `portal/nutrition_imports.py`: queries consistently include athlete id and raw uploads
  are not retained. The route-level athlete owner is still globally selectable by any
  coach.
- `portal/nutrition_prescriptions.py` and
  `portal/repositories/nutrition_prescriptions.py`: athlete scoped, not tenant scoped.
- `portal/repositories/meal_plans.py`: `list_drafts`, `get_draft`, `save_draft`,
  `list_assignments`, and `get_assignment` are global/direct-id operations and do not
  enforce the existing `coach_id`. This is a highest-risk IDOR boundary.
- `portal/meal_plan_delivery.py`: coach handlers rely on role only. Athlete handlers
  use the authenticated athlete id and are the strongest existing compatibility model.
- There is no generated PDF/blob model or persisted PDF file metadata in this
  repository. Meal plans are JSON snapshots. Any future PDF/object must store tenant,
  athlete/assignment, object key, checksum, content type, size, creator, and lifecycle
  timestamps; object keys and signed-download authorization must be tenant scoped.

### Competition and performance analytics

- `portal/meet_day.py`: meet and athlete lists are global; meet/entry/lift mutation uses
  direct ids. Child-vs-parent checks exist in places, but no tenant can be checked.
- `portal/services/{meet_day,competition_day,competition_bodyweight}.py`: ownership is
  inferred through entry athlete or global meet.
- `portal/api/athlete_performance.py` accepts any athlete id. Athlete users are protected
  by the central path-id check; every coach can query every athlete.
- `portal/services/{athlete_performance,performance_charts,performance,
  performance_decisions,coach_athlete_performance,training_performance,
  weekly_programming_intelligence,athlete_dashboard,athlete_state}.py`: most detailed
  queries correctly constrain athlete id, but none accept tenant context. Joins are
  therefore safe only while athlete ids are globally trusted.

### Applications, leads, files and storage

- `portal/coaching_applications.py` lists and mutates a global application inbox;
  `coaching_applications` has no owner or acquisition-site key.
- `portal/lead_magnets.py` writes `lead_captures` as a global root. There is no private
  tenant inbox in this code yet, but future access would be ambiguous.
- Nutrition uploads are parsed in memory and discarded; only source filename, checksum,
  preview JSON and results persist. Those records inherit athlete ownership.
- `external_coaching_reviews.external_url` is user-supplied external metadata and is
  athlete-owned only. No uploaded review media is stored.
- Repository/status/release-evidence files are operational filesystem inputs, not
  customer files. Static assets and lead-magnet JSON are application content.
- No S3/Azure Blob/GCS bucket adapter, tenant object prefix, file ACL model, or signed
  download route was found.

### Admin and support surfaces

- `portal/views.py`, `portal/api/{executive,engineering,history,platform,
  recommendations}.py`, `portal/release_readiness.py`, and associated dashboard
  services are available to any coach. They expose platform-wide operational data.
- There is no separate platform-admin/support identity, no tenant impersonation grant,
  no reason/expiry field, and no audit event for support access.
- `portal/repositories/platform_snapshot_repository.py` is intentionally global and
  should remain outside customer tenant tables, but access should move to a platform
  role rather than tenant coach.

## Candidate tenant boundary

Use an additive `tenants` (or `coaching_organisations`) root representing one data
controller/business, not an individual coach. Add `tenant_memberships` linking users to
tenants with roles such as `owner`, `coach`, and later narrowly scoped staff. Keep
`users` as global login identities. Add `athletes.tenant_id`; athlete login continues to
link to its athlete, whose tenant becomes authoritative.

The request context should resolve exactly one active membership and expose an immutable
`TenantScope(tenant_id, user_id, role)`. Repository/service methods should require that
scope. Do not rely on callers remembering `.filter_by(tenant_id=...)`; central scoped
load/list helpers should return 404 for foreign objects. Platform admin/support must be
a distinct global role with explicit, expiring, reasoned tenant access and audit logs.

Classification:

- Tenant-owned roots: athletes, meets, coaching applications, lead captures, meal-plan
  templates, tenant-created warmup protocols/templates, and future stored files.
- Inherit through athlete: programming, logs/results, check-ins, nutrition, services,
  athlete state, reviews, assignments and competition entries/lifts.
- Platform-global: user identity, canonical exercise/template/protocol catalogue,
  platform snapshots and release/engineering telemetry.
- Actor references are attribution only; they never establish ownership.

## Required foreign keys, constraints and indexes

Add these in a later migration; this audit intentionally adds none.

1. `tenants(id, slug, status, created_at)` with unique `slug`.
2. `tenant_memberships(tenant_id, user_id, role, status, created_at)` with FKs,
   unique `(tenant_id,user_id)`, and indexes `(user_id,status)` and
   `(tenant_id,status,role)`.
3. Non-null `athletes.tenant_id` after backfill; indexes `(tenant_id,status,id)` and
   `(tenant_id,last_name,first_name,id)`. Decide deliberately whether athlete email is
   globally unique (identity) or unique `(tenant_id,email)` (business contact).
4. Tenant ids on independent roots: `meets`, `coaching_applications`, `lead_captures`,
   `meal_plan_templates`, tenant-authored warmup protocols/day templates, and file
   metadata. Add the list/order indexes used by each inbox.
5. Prefer composite parent keys `(tenant_id,id)` and composite FKs on sensitive direct
   children. At minimum add tenant id to high-volume/high-risk leaves used by direct-id
   APIs: blocks, session logs, check-ins, nutrition records/prescriptions/import jobs,
   meal-plan assignments, meet entries, programme revisions, reviews and files. This
   enables database-enforced same-tenant joins and later PostgreSQL RLS.
6. Add a real FK from meal-plan assignment to template. Because templates use UUID text,
   use `(tenant_id,template_id)` -> template `(tenant_id,id)`; also validate publisher
   membership and athlete tenant.
7. Add composite consistency constraints for dual-root records: log athlete/session,
   revision athlete/block, warmup athlete/session, daily-nutrition athlete/job, review
   athlete/log/result/observation, and meet entry meet/athlete.
8. Index every access pattern tenant-first: `(tenant_id,id)`, tenant plus status/date,
   and tenant plus current uniqueness columns. Keep existing child FK indexes.

## Highest-risk cross-tenant query paths

Ordered by likely confidentiality/integrity impact:

1. Global coach bypass in `auth._authorize_request`: one missing membership check
   compromises every coach surface.
2. Meal-plan direct-id repository and global draft/assignment lists: sensitive nutrition
   content can be read or overwritten even though templates already carry `coach_id`.
3. Athlete index/detail/onboarding/account lifecycle: exposes PII, notes and allows
   invitation/password-reset actions for any athlete.
4. Check-in global inbox and direct review mutations: health-adjacent wellbeing and
   nutrition data plus coach response integrity.
5. Programming direct-id mutations: blocks/weeks/sessions/prescriptions can be modified
   across tenants; nested ids are often loaded without an ownership predicate.
6. Meet-day global roots: competition data and attempts are globally listable/mutable,
   and a meet can currently mix future tenants.
7. Coaching applications and leads: sensitive applicant PII has no ownership root.
8. Performance/chart endpoints: broad athlete-id enumeration yields derived training,
   bodyweight, nutrition and competition information.
9. Operational/admin APIs: tenant coaches would receive global infrastructure/security
   information unless roles are separated.
10. Future object storage: a global object key or guessable assignment id would bypass
    otherwise-correct page authorization unless downloads re-resolve tenant ownership.

## Safe production migration sequence

Use expand/backfill/validate/enforce/contract. Never edit `alembic_version` manually.

1. Inventory and backup: verify there is exactly one intended legacy coaching business,
   enumerate every orphan/dual-root inconsistency, duplicate email, dangling template id
   and actor mismatch. Block migration on unexplained rows; do not silently guess.
2. Expand: create tenant and membership tables. Insert one deterministic `legacy`
   tenant. Add nullable tenant columns and new indexes concurrently where PostgreSQL
   permits. Make no authorization behaviour change yet.
3. Backfill roots: assign every existing athlete, coach membership, meal template, meet,
   application and lead to `legacy`. Platform-global records remain unowned. Record row
   counts and checksums before/after.
4. Backfill descendants from their authoritative parent. For dual-root rows, compare all
   paths and quarantine/fail on disagreement. Backfill file/object metadata before any
   tenant-aware download is enabled.
5. Validate: add FKs/check constraints as `NOT VALID` where supported, validate after
   backfill, then make required tenant columns non-null. Add composite same-tenant FKs.
   Run negative two-tenant tests and query-plan checks.
6. Compatibility release: resolve the sole membership automatically for legacy coach
   users, but still pass explicit `TenantScope` into new repositories. Keep URLs and UI
   unchanged. Add audit logging for scope and denied foreign ids.
7. Enforcement release: change all coach loads/lists/mutations to tenant-scoped
   repositories and separate platform-admin endpoints. Return 404 for cross-tenant ids.
   Optionally enable PostgreSQL RLS only after every worker/CLI/job establishes tenant
   context and connection-pool reset is proven.
8. SaaS enablement: only after isolation tests pass, allow creation of another tenant.
   Monitor denied access, missing scope and unowned-row metrics. Retain rollback by
   leaving additive tenant data in place; rollback application code, not backfilled ids.
9. Contract cleanup in a later release: remove temporary legacy fallback only after all
   web, CLI, scheduled job, import and support paths require explicit scope.

## Compatibility strategy

Create a single legacy tenant during migration and one active owner membership for each
existing coach user. If a user has exactly one membership, select it server-side and
preserve all current routes, templates, forms and programming workflow. Do not add a
tenant picker to the coach UI for the single-membership case. Athlete sessions derive
scope from `user.athlete.tenant_id`, preserving current athlete URLs and 404 behaviour.

For a transition period, an adapter can provide `legacy_scope()` only when the database
contains exactly one tenant and the authenticated user has exactly one active membership.
Fail closed otherwise. Never use “first tenant”, a configured global coach id, email
domain, or absence of a tenant parameter as authorization evidence.

## Verification gates for implementation

- Two tenants with overlapping human-readable names; each owner can list/read/mutate
  only its own records across every domain named in this audit.
- Foreign ids return 404 on GET and mutation; bulk endpoints and nested child ids cannot
  cross parents.
- Athlete A cannot access athlete B, including ids not named `athlete_id` in the URL.
- Cross-tenant composite FK attempts fail at the database boundary.
- Background jobs, imports, exports/PDF generation, object downloads, CLI commands and
  support access all require an explicit scope.
- Legacy fixture row counts/content remain unchanged except additive tenant keys; all
  existing single-coach focused tests continue to pass.

single-business until explicit tenant enforcement and negative isolation tests land.
