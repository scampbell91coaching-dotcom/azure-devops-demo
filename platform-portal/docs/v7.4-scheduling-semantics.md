# V7.4 scheduling semantics

## Current persisted truth

An active `TrainingBlock` is the athlete's published programme. Weeks are ordered by `TrainingWeek.position`; sessions within a week are ordered by `TrainingSession.position`. `day_label` is descriptive free text, not a date or guaranteed weekday. Blocks, weeks and sessions have no persisted planned-date field. `created_at`, log timestamps, check-in dates and the athlete-state `training_start_date` describe other events and must not be treated as programme anchors.

Consequently, the current product must say **Date not set**. It must never imply that a session is due today from its `day_label` or position.

## Shared athlete and coach answers

- **Today:** a session only when an explicit resolved `planned_on` equals today and it is unfinished. With the current persistence model this is “nothing assigned to a calendar date.”
- **Next:** the earliest unfinished explicit planned date when dates are supplied; otherwise the first unfinished session in `(week.position, session.position)` order. An overdue unfinished dated session remains next.
- **Current week:** the week containing that next session. This is labelled “current progress week,” not calendar week. When every session is complete, the block is complete and there is no current week.
- **Belongs when:** an explicit planned date when available; otherwise “Date not set · programme order,” alongside its week and session positions.
- **Dates shift:** completion records remain complete and published prescriptions/order are not rewritten. Until a rescheduling policy is persisted, athlete and coach must confirm the changed next session; the UI says so explicitly.

`TrainingSessionLog.status == completed` is the only completion state that removes a session from today/next selection. In-progress and unlogged sessions remain candidates. Empty weeks contribute no candidate. If there is no active block, there is no current/next session.

## Holiday/Travel Mode seam

`project_training_schedule(block, logs, today=..., planned_dates=...)` is a read-only projection. A later Holiday/Travel resolver should produce a session-id-to-date mapping (and eventually richer status/reason metadata) from immutable base assignments plus dated exceptions, then pass the resolved mapping into this function. The resolver must not mutate published session order, prescriptions or completed logs. Persistence, exception authoring and policy decisions are deliberately outside V7.4.

Mixed dated/undated inputs are transitional: unfinished dated sessions take precedence; undated sessions remain visible in programme order and clearly lack a date. A later persisted calendar must validate uniqueness/conflicts and expose the source of each resolved date.

## Test contract

Unit coverage fixes the behavior for missing dates, year boundary dates, today/future/overdue sessions, completed sessions and progress crossing into another week. Mobile E2E at 320px asserts that the date-missing explanation is visible on dashboard and programme without horizontal overflow.
