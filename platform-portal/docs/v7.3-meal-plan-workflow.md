# V7.3 meal-plan workflow

## Decision summary

Meal plans should be a versioned, coach-authored layer beneath an athlete's macro prescription. A published assignment is an immutable snapshot: later template edits, food-fact corrections, or prescription changes must not silently rewrite what the athlete was asked to follow. The first release should use a small coach-curated food catalogue, support fixed and hybrid days, show reconciliation before publishing, and collect simple plan-specific adherence alongside the existing weekly check-in.

The migration-free reference implementation is `portal/services/meal_plans.py`. It establishes calculation and validation semantics without selecting a database representation.

## Existing platform seams

The current nutrition feature is three adjacent workflows rather than one prescription system:

- `NutritionCheckIn` is an athlete-entered weekly snapshot with self-entered targets and actual averages, 1–10 adherence and wellbeing scores, qualitative notes, and coach response/review state. The athlete route validates ranges and updates bodyweight.
- `WeeklyCheckin` has configurable training/nutrition modules. Its nutrition section stores average calories/macros, source and period, steps, adherence, and notes. Coaches can review it. MyFitnessPal data can prefill this form, and submission preserves a snapshot.
- `DailyNutrition` stores per-athlete, per-date aggregate calories/macros/fibre/bodyweight from consented MyFitnessPal file imports. Preview, size/type checks, idempotent day updates, isolation, disconnect, and deletion exist. It does not retain meal-level rows and therefore cannot identify whether a prescribed meal was followed.
- `nutrition_dashboard` combines dedicated and weekly check-ins for coach visibility, but only surfaces calories, protein, bodyweight, and adherence. There is no authoritative macro-prescription model, meal template, assignment, food catalogue, or meal-plan adherence event today.

Consequences: imported daily totals can corroborate daily macro adherence, but must not be treated as meal adherence; the existing check-in target fields are historical self-reported snapshots, not the source of truth. During transition, a published assignment should snapshot an externally supplied macro target. Later, a dedicated macro-prescription service can supply that snapshot.

## End-to-end workflow

1. **Coach defines or selects a macro prescription.** It has an athlete, effective range, day type(s), calories, protein, carbohydrate, fat, optional fibre, provenance, and revision identifier.
2. **Coach builds a reusable template.** The coach names ordered days and ordered meals, then chooses a small set of foods and portions. Foods contain an explicit reference amount/unit and a nutrition-fact snapshot. A flexible day holds only a macro target; a hybrid day combines fixed meals with a flexible allowance.
3. **System calculates continuously.** Food portions roll up to meal, fixed-day, flexible allowance, and complete-day totals. Each day reconciles against the selected prescription and names every field outside tolerance.
4. **Coach previews and publishes an assignment.** Publishing requires an effective date, athlete, prescription snapshot, template revision, and zero blocking validation errors. An out-of-tolerance plan requires an explicit coach override reason. Publication freezes the assignment revision.
5. **Athlete views the active assignment.** The view is date/day-type aware, retains declared meal order, shows portions and permitted substitutions, distinguishes fixed from flexible allocation, and always shows daily target and planned total. Athlete changes are limited to declared substitutions; they never edit the coach's template.
6. **Athlete records feedback.** MVP feedback is a per-day completion state (`followed`, `partly_followed`, `not_followed`, `not_applicable`) plus optional note and selected substitutions. Weekly check-in displays a derived completion summary and still asks the athlete's 1–10 adherence/wellbeing questions.
7. **Coach reviews.** The coach sees assignment adherence, imported daily-total comparison when available, notes, and existing check-in signals. A coach may create a new assignment revision or apply a dated, reasoned athlete-specific override. Past assignments/events remain unchanged.

Template lifecycle: `draft -> published -> archived`. Assignment lifecycle: `draft -> scheduled -> active -> superseded|ended`. A template is reusable; an assignment binds one immutable template revision and one immutable prescription snapshot to one athlete and effective interval.

## Domain language and validation

### Value objects

- `MacroTotals`: non-negative calories, protein, carbohydrate, fat, and fibre, represented with decimal arithmetic. Calories remain supplied data; do not silently replace them with `4P + 4C + 9F`, because labels and fibre rounding differ.
- `FoodSnapshot`: stable key, display name, positive reference amount, unit, macro totals, and eventually source/verified timestamp/allergen notes. It is intentionally not a global food database.
- `MealItem`: stable key, food snapshot, positive amount in the snapshot's unit, and optional serving note.
- `Meal`: stable key, non-empty name, positive unique position, ordered items, and calculated totals.
- `MealPlanDay`: stable key, name, unique position, mode, ordered meals, flexible target, and calculated totals.
- `MacroTolerance`: coach-configurable absolute tolerances; MVP defaults are 50 kcal, 5 g protein, 10 g carbohydrate, 5 g fat, and 5 g fibre.
- `Substitution`: named, pre-approved replacement of exactly one item slot. Its displayed macro delta is calculated, not entered.
- `CoachOverride`: actor, reason, target, replacement, creation time/effective range, and parent revision. It is an audit event, not an in-place mutation.

### Invariants

- IDs, names, units, actors, and override reasons are required where applicable; amounts and positions are positive.
- Day and meal positions are unique in their parent. Item IDs are unique within a meal and assignment-level item keys must resolve exactly once when substituted or overridden.
- Fixed days contain fixed meals and no flexible allowance. Flexible days contain a macro allowance and no fixed meals. Hybrid days require both.
- Macro values and food facts cannot be negative. Zero is valid (for example, zero carbohydrate).
- Publishing requires at least one day, at least one item on every fixed component, a complete target, an effective date, and a fresh reconciliation result.
- Assignment dates for the same athlete/day type must not ambiguously overlap. Resolution is explicit, never “latest row wins.”
- Athlete substitutions must be whitelisted, active for the assignment revision, and applicable to the target slot. The result is re-totalled and visibly compared with the target.
- Overrides require coach authorization, reason, and optimistic concurrency/revision match. Every publication, substitution selection, override, and adherence event records actor and timestamp.
- Historical food snapshots and assignments are immutable. Deleting/archiving a catalogue food does not damage history.

## Reconciliation rules

For each assignment day:

`planned = sum(fixed meal items) + flexible allowance`

`delta = planned - prescription snapshot`

A field is matched when `abs(delta) <= tolerance`. The result contains target, planned total, signed delta, overall status, and the exact outside-tolerance fields. Boundary values are accepted. All five fields reconcile independently; a calorie match cannot hide a protein miss.

Drafts may be outside tolerance. Publishing is blocked by default. A coach can publish outside tolerance only with a reasoned assignment-level override; the UI must show the remaining deltas and audit marker. Prescription changes never mutate an active assignment: offer “create revision and reconcile” instead. For a hybrid day, the UI may suggest the non-negative remainder (`target - fixed total`), but the coach confirms it; a negative remainder is a blocking error, not silently clamped.

Imported actuals reconcile separately as `actual vs assigned target`. Missing/partial import days remain unknown and are excluded from averages with coverage shown. They never change the prescribed plan.

## Substitutions and overrides

A substitution belongs to a template revision and one item slot. It replaces the entire slot (food plus amount), preserves meal order, and shows macro/portion delta before selection. It should normally be near-equivalent, but equivalence is policy rather than hidden normalization. MVP supports one-for-one swaps only; multi-item exchange groups can follow later.

Athlete selection creates a dated selection event against the assignment, leaving both template and assignment unchanged. If a substitution is withdrawn, previous selections remain readable.

A coach override is athlete-specific and higher priority than the template/substitution default. MVP needs replace-item/portion and flexible-allowance adjustment. Add/remove meal and schedule changes can use a new assignment revision initially. Resolution order is: assignment snapshot -> applicable coach override -> athlete-selected permitted substitution. A substitution cannot replace an override unless the override explicitly permits it. Conflicts or missing targets fail loudly.

## Future persistence (no migration in V7.3 design work)

Suggested aggregates/tables, deliberately not column-level DDL:

- `meal_plan_templates` and immutable `meal_plan_template_revisions`
- revision-owned `meal_plan_days`, `meals`, and `meal_items` with explicit positions
- small `foods` catalogue plus immutable `food_nutrition_snapshots`
- revision-owned `meal_item_substitutions`
- `meal_plan_assignments` with athlete, effective interval, lifecycle, template revision, prescription snapshot/revision, and publication audit data
- `meal_plan_overrides` as append-only, actor/reason/effective-dated events
- `meal_plan_adherence_events` and `meal_plan_substitution_selections`

Use integer/UUID identity independently of display order. Store decimal quantities with explicit precision and units. Snapshot food facts and prescription values into published revisions. Add foreign keys, athlete/effective-date indexes, uniqueness for parent/position, and optimistic revision/version fields. A repository adapter should hydrate the domain objects; ORM rows must not leak into reconciliation logic.

Shopping-list generation later should consume the resolved assignment days over a requested date range, expand selected substitutions/overrides, convert only compatible units, group by stable food snapshot and unit, and retain an “uncombined” bucket when conversion is unsafe. It must be derived output, not hand-maintained state.

## Route and API flow

Coach HTML routes (server-rendered MVP):

- `GET/POST /coach/meal-plan-templates`
- `GET/POST /coach/meal-plan-templates/<id>/revisions/<revision>` for draft editing
- `POST .../reconcile` for preview; `POST .../publish` with revision token
- `GET/POST /coach/athletes/<athlete_id>/meal-plan-assignments`
- `POST /coach/meal-plan-assignments/<id>/overrides`
- `GET /coach/meal-plan-assignments/<id>/adherence`

Athlete routes:

- `GET /athlete/meal-plan?date=YYYY-MM-DD`
- `POST /athlete/meal-plan/assignments/<id>/days/<day>/substitutions`
- `POST /athlete/meal-plan/assignments/<id>/days/<date>/adherence`

JSON parity can live under `/api/v1` with the same resources. Commands accept an idempotency key and expected revision; responses return resolved plan, reconciliation, provenance, and revision. Return 400 for malformed values, 403 for role denial, 404 for inaccessible cross-athlete resources, 409 for stale revision/date overlap, and 422 for domain validation. Route handlers authorize and translate; application services resolve assignment/repository state; pure domain services calculate.

Integrations:

- Prefill weekly-check-in assigned targets from the assignment snapshot, labelled “assigned meal plan,” but preserve the submitted check-in snapshot.
- Compare `DailyNutrition` only at date-level totals and show provider/coverage/partial status.
- Feed plan adherence into the existing coach nutrition/dashboard view as another provenance-labelled record; do not collapse it into self-reported 1–10 adherence.

## First-MVP acceptance criteria

1. A coach can create a draft template with named, ordered days/meals and coach-curated food snapshots/portions, without a third-party food database.
2. Fixed and hybrid days calculate per-item, per-meal, fixed subtotal, flexible allowance, and daily totals using decimal arithmetic. Flexible-only is supported by the domain/API even if its editor is deferred.
3. Invalid amounts, negative macros, duplicate positions/keys, incomplete mode composition, and ambiguous references are rejected with field-level errors.
4. A coach can define one-for-one substitutions; the athlete sees only permitted options and sees the resulting macro delta before confirming.
5. Every day reconciles all macro fields against an immutable prescription snapshot using visible tolerances and signed deltas.
6. Publishing outside tolerance is blocked unless an authorized coach supplies a non-empty reason; the exception remains visible and auditable.
7. Assigning a published revision to an athlete creates a dated immutable snapshot. Template edits or food updates do not change it.
8. The athlete sees only their current assignment, in declared meal order, with fixed/flexible sections clearly labelled. Cross-athlete access returns 404 under the established authorization pattern.
9. The athlete can record daily completion state, note, and substitution selection idempotently. Historical records retain the assignment revision used.
10. The coach can replace an assigned item/portion or flexible allowance with actor, reason, date, parent revision, and recalculated totals; stale edits conflict rather than overwrite.
11. Existing weekly check-in can display assigned targets and a plan-completion summary without changing historical submissions. Imported daily totals are optional corroboration and clearly identify missing/partial days.
12. Unit/domain tests cover aggregation, mode validation, tolerance boundaries, reconciliation deltas, substitution/override immutability, missing targets, ordering, and authorization/service conflict paths.
13. The implementation introduces no migration or production/deployment change in this design slice.

## Deliberate deferrals

Barcode scanning, recipe decomposition, restaurant menus, micronutrients, automatic meal recognition, a comprehensive branded-food database, dietetic/medical recommendations, multi-item exchange algebra, automatic portion optimization, and shopping-list UI are outside the first MVP. The proposed snapshot and resolved-plan boundaries allow these to be added without changing the core workflow.
