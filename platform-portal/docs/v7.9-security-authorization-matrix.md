# V7.9 coaching delivery authorization matrix

## Scope and conventions

This matrix is the security contract for the V7.9 coaching delivery work. It
does not introduce a new authentication design. The portal continues to use the
session principal loaded into `g.current_user`, the central endpoint allowlist
in `portal.auth`, and the global session-bound CSRF check for unsafe HTTP
methods.

The established response convention is:

- `401` (JSON/API) or login redirect (browser) when there is no authenticated
  principal;
- `403` when the authenticated role may not perform the class of operation, or
  when an enabled service is required for a current action;
- `404` when an athlete asks for another athlete's resource, or a resource does
  not exist, so existence is not disclosed across the athlete boundary;
- `400` for a missing or invalid CSRF token, before mutation logic runs;
- `409` for a stale, replayed, already decided, or history-locked operation.

Coach access currently means any authenticated coach. There is no coach-to-
athlete ownership/tenant relation in the present model, so this audit must not
pretend one exists. Add that relation separately before supporting multiple
coaching tenants.

The server must derive an athlete principal's identity from
`g.current_user.athlete_id`. A path, form field, query parameter, proposal
payload, upload metadata, or browser session hint is never sufficient identity
evidence. Route-scoped IDs may select a resource only after ownership is
checked. Coaches may select an athlete explicitly because their role is the
authorized selector.

“Allow” always assumes authentication, valid CSRF for browser mutations, valid
input, and a resource in the caller's permitted scope.

## Current audit result

### Enforced now

- Central authentication denies every coaching route to athlete users unless its
  endpoint is explicitly athlete-allowlisted. Athlete routes with an
  `athlete_id` path value return `404` when it differs from the authenticated
  athlete.
- Global CSRF enforcement covers all non-safe browser methods and accepts either
  the injected form field or `X-CSRF-Token`.
- Programming and warmup mutation endpoints are coach-only by omission from the
  athlete allowlist. Athlete session reads verify ownership; warmup mutations
  derive ownership through the training session; the first athlete read creates
  an immutable snapshot and subsequent edits return `409`.
- Block Factory is coach-only. Acceptance reloads the athlete from the stored
  proposal, verifies a server-keyed HMAC, recomputes source data, and uses an
  atomic `proposed` transition to prevent replay.
- Nutrition import checks athlete ownership, nutrition entitlement, upload
  limits, and binds commits to both job ID and athlete ID. V7.9 removed preview,
  commit, and disconnect from the athlete endpoint allowlist, closing the
  coach-only mutation gap while retaining the athlete's own read view.
- Service changes are coach-decorated, CSRF-protected, attached to a loaded
  athlete, and record the authenticated user ID.

### Not yet exposed as delivery routes

Macro prescriptions and meal plans are schema-independent domain services only;
there are no create, publish, current, or history HTTP endpoints to authorize.
Warmup recommendations likewise have no dedicated accept/reject routes. The
matrix above is mandatory acceptance coverage when those adapters are added.
Domain provenance fields are audit metadata, not an authorization control:
callers must not be allowed to establish their own role or actor identity.

### Known entitlement gaps to close with delivery implementation

Training entitlement is not currently checked by programming, warmup, or Block
Factory routes. Those routes predate the delivery matrix. Add one service-layer
guard at each new/current action boundary before exposing V7.9 delivery; do not
apply it to immutable historical reads. Existing nutrition import mutations do
use the nutrition entitlement guard. Avoid broad UI-only gating because direct
requests must be denied too.

## Test placement

`tests/test_v79_authorization_boundaries.py` covers the previously missing
cross-workflow role and CSRF assertions plus nutrition read ownership.
Feature-specific suites retain detailed integrity, history-lock, upload,
entitlement, and replay coverage. Each future route named above must add the
remaining cells beside its feature tests rather than weakening this matrix.
