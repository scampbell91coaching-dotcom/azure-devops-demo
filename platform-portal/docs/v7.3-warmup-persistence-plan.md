# V7.3 warm-up persistence and UI integration plan

## Outcome and scope

V7.2 already provides a pure, deterministic warm-up domain in
`portal.services.warmup_plans`. V7.3 should persist inputs and resolved history around
that service, rather than turn warm-ups into ordinary exercise prescriptions. This is
the smallest path that gives coaches reusable protocols and explicit session control,
and gives athletes a stable plan before their work sets.

This proposal does not include an Alembic revision. It specifies the later revision
and adds only schema-independent ports and orchestration now.

## Existing integration points inspected

- `TrainingBlock -> TrainingWeek -> TrainingSession` owns the programmed session;
  each block already identifies its athlete.
- `ProgrammingLiftSlot` is the canonical squat/bench/deadlift exposure and should be
  the source of lift-family context. A session may contain several lift slots.
- `ExercisePrescription` owns work and assistance prescriptions. Warm-up steps must
  remain separate so they do not distort volume, set logging, or existing ordering.
- `TrainingSessionLog` is the athlete/session assignment and completion record. Its
  unique `(athlete_id, session_id)` pair is a useful snapshot boundary, but a warm-up
  plan must also be viewable before the log is started.
- Coach editing is centred on `GET /programming/sessions/<session_id>`; athlete use is
  centred on `GET|POST /athlete/programme/sessions/<session_id>`.
- Existing route, programming-domain, session-lifecycle, athlete-dashboard, training
  log, and warm-up-domain tests establish the compatibility boundaries.

## Persistence design

Use immutable protocol versions. Editing a published protocol creates a new version;
old assignments and snapshots retain their version.

### Proposed tables

`warmup_protocols`

- `id` bigint primary key; `stable_key` varchar(80); `version` integer; `name`
  varchar(160); `description` text nullable; `priority` integer default 100;
  `status` varchar(20) (`draft`, `active`, `retired`); `created_by_user_id` foreign key;
  `created_at`, `published_at`.
- Unique `(stable_key, version)`. Index `(status, priority, stable_key)`.
- Published rows are immutable at the application boundary.

`warmup_protocol_applicability`

- `id`, `protocol_id` foreign key with cascade delete, `lift_family` varchar(20)
  nullable, `athlete_tag` varchar(80) nullable, `session_tag` varchar(80) nullable.
- Exactly one selector is non-null. Lift family is constrained to squat, bench, or
  deadlift. Multiple rows of one kind mean OR; selector kinds combine with AND.
- Athlete-specific selection does not belong here; it is an assignment.

`warmup_protocol_steps`

- `id`, `protocol_id` foreign key with cascade delete, `stable_key` varchar(80),
  `position` integer, `phase` integer constrained to 10/20/30/40, `name`, `kind`
  constrained to reps/duration/barbell, `sets`, `reps`, `duration_seconds`,
  `percentage`, `load_kg`, `rest_seconds`, `notes`.
- Unique `(protocol_id, stable_key)` and `(protocol_id, position)`; positive position.
- Check constraints mirror `WarmupInstruction`: required values by kind, exactly one
  barbell load target, positive counts, and valid percentage.

`warmup_protocol_assignments`

- `id` UUID/string primary key, `protocol_id` foreign key (the pinned version),
  `athlete_id` foreign key, `session_id` foreign key nullable, `lift_slot_id` foreign
  key nullable, `assigned_by_user_id`, `reason`, `active`, `created_at`, `ended_at`.
- At least one of session or athlete is present; a lift-slot assignment requires its
  session to match the slot. Prefer session + lift slot for lift-specific protocols,
  session for whole-session preparation, and athlete-only for a coach default.
- Partial unique indexes prevent two active assignments of one protocol version to
  the same target. Resolution precedence is lift slot, session, then athlete default.
  Duplicate protocol versions collapse to one application while every contributing
  assignment ID remains in provenance.

`warmup_plan_overrides`

- `id` UUID/string primary key, `athlete_id`, `session_id`, `lift_slot_id` nullable,
  `action` (`remove`, `replace`, `append`), `target_step_key` nullable, replacement
  step payload in typed columns matching protocol steps, `reason`,
  `created_by_user_id`, `created_at`, `supersedes_id` nullable.
- Rows are immutable audit events. Removal requires a target; replace requires target
  and replacement; append requires replacement. Do not overwrite or delete history.

`warmup_plan_snapshots` and `warmup_plan_snapshot_steps`

- Snapshot: `id`, `athlete_id`, `session_id`, `training_session_log_id` nullable,
  `lift_slot_id` nullable, `resolved_at`, `resolver_version`, and a uniqueness key for
  the assignment revision (or monotonically increasing revision).
- Steps contain final order, all typed instruction values, notes, source protocol key
  and version, assignment ID(s), override ID, parent source fields, and reason/actor.
- Create the first snapshot when the athlete opens/starts a session; attach it to the
  log when created. Reopening an in-progress or completed log reads its snapshot.
  Coach edits create a new revision only before completion and require confirmation
  if the athlete has started. Completed logs never drift.

All foreign keys should use cascade only for unpublished protocol children. Audit and
snapshot references should restrict deletion or retain denormalised source identity.
Use UTC timestamps. The migration must backfill nothing because no warm-up tables
exist; deploy tables before enabling routes. Downgrade drops only these new tables in
reverse dependency order.

## Service and repository boundary

The domain module now exposes:

- `WarmupProtocolRepository` for active, validated domain protocol versions;
- `AssignedWarmupPlanRepository` for assignments and immutable overrides scoped to a
  supplied `WarmupContext`;
- `WarmupPlanSnapshotRepository` for explicit resolved-plan writes;
- `AssignedWarmupPlanService`, which fails closed on missing pinned versions, applies
  only assigned and applicable protocols, retains assignment IDs, and snapshots only
  when explicitly requested.

The future SQLAlchemy adapter owns queries, authorization scoping, and transactions.
It maps ORM rows into domain values; routes never assemble plans from rows. Keep
`build()` read-only. A route starts a transaction and requests `save_snapshot=True`
only at the snapshot boundary. Concurrent creation should use a unique constraint and
reload the winner after an integrity conflict.

## Coach experience and APIs

Add a **Warm-up** panel above “Main lifts” on the existing session builder. For every
lift slot it shows the resolved phases, protocol/version badges, applicability, and
override markers. Coaches can assign from a searchable protocol library, preview the
resolved result, remove/replace/append a step with a required reason, reset an
override by superseding it, and publish the plan to the athlete. A session-wide
general protocol is shown once, not duplicated per lift.

Add a protocol library at `GET /programming/warmups`, with create/edit-draft/publish/
retire flows. Keep protocol authoring separate from the session sheet.

Proposed HTML/API endpoints:

- `GET /programming/warmups` and `GET|POST /programming/warmups/new`
- `GET|POST /programming/warmups/<stable_key>/versions/<version>`
- `POST /programming/warmups/<stable_key>/versions/<version>/publish`
- `GET /api/programming/sessions/<session_id>/warmups?lift_slot_id=<id>` (preview)
- `POST /api/programming/sessions/<session_id>/warmup-assignments`
- `DELETE /api/programming/sessions/<session_id>/warmup-assignments/<id>` (ends it)
- `POST /api/programming/sessions/<session_id>/warmup-overrides`
- `POST /api/programming/sessions/<session_id>/warmup-overrides/<id>/supersede`
- `POST /api/programming/sessions/<session_id>/warmups/publish`

All mutations require coach authorization, CSRF protection, same-athlete/session
ownership checks, validated lift-slot membership, and a reason for auditable changes.
Return 409 for edits racing a newer revision and 422 for domain validation errors.

## Athlete experience and API

On the existing athlete session page, place **Warm-up** after session notes and before
the work-set form. Show phases as one ordered checklist, grouped by lift exposure when
necessary. Each item displays name, sets/reps or time/load, rest, and coach notes.
Protocol IDs, internal tags, override reasons, and diagnostic language stay out of the
athlete UI. The plan is instructional, not a medical claim.

`GET /api/athlete/programme/sessions/<session_id>/warmups` returns the athlete-owned
snapshot (or creates the initial snapshot transactionally). The existing session GET
can initially render the same view model server-side, avoiding a JavaScript dependency.
Warm-up checkbox state can remain client-local in V7.3; persisting completion is a
separate product decision and should not be smuggled into training set results.

## Acceptance criteria

1. A coach can publish an ordered, versioned protocol and assign its pinned version to
   an athlete, session, or session lift slot.
2. Only protocols whose explicit applicability matches the canonical lift-slot and
   recorded tags resolve; absence of context never triggers inference.
3. Resolution is deterministic by phase, priority, protocol identity, and step order.
4. A coach can preview and publish required-reason remove/replace/append overrides;
   provenance retains protocol version, assignment, override, actor, reason, parent,
   and resolver version.
5. Missing/retired pinned data fails visibly and does not silently substitute a newer
   protocol version.
6. An athlete sees the ordered warm-up before work sets on mobile and desktop, with an
   accessible heading/list and complete instruction units.
7. Once a session starts, its snapshot remains stable; completed history never changes
   when a protocol is edited or retired.
8. Athlete and coach authorization prevents cross-athlete access; mutation endpoints
   enforce CSRF and ownership.
9. Existing prescriptions, lift-slot ordering, training logging, and route contracts
   remain unchanged.
10. Unit tests cover mapping validation, assignment precedence/deduplication, scopes,
    overrides, missing versions, ordering, snapshot idempotency/concurrency, and
    provenance. Route tests cover authorization, validation, and rendered surfaces;
    one end-to-end test covers coach publish through athlete display.

## Delivery sequence

1. Review this model and create one Alembic revision plus ORM adapters in a later task.
2. Add adapter contract tests and snapshot concurrency tests.
3. Add read-only coach preview, then guarded mutations and protocol authoring.
4. Add server-rendered athlete snapshot display.
5. Run focused tests, the full portal suite, migration upgrade/downgrade checks, and
   accessibility/end-to-end coverage before enabling the feature.
