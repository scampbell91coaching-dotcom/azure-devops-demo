# V7.9 blue/green current implementation review

Audit base: `7d77bdc5431c9bc4a4fe15651eded3426cc6d0e5`  
Review type: repository-only, read-only design audit  
Decision: **NO-GO for a blue/green production cutover from the current manifests**

This review does not authorize a cluster query or change, production change, merge, or deployment. It compares the Git-declared Kubernetes, Argo CD, workflow, migration, storage, networking, and operational contracts with the fixed-slot design in [V7.6 Blue/Green implementation readiness](v7.6-blue-green-implementation-readiness.md).

## Executive assessment

The V7.6 blue/green design has not been implemented. The private portal remains one `Deployment/platform-portal-private`, one stable Service selecting the broad `app: platform-portal-private` label, and one automated Argo CD Application owning the whole manifest directory. There are no Blue or Green Deployments, no slot labels, no direct slot Services, no inactive-slot promotion, and no selector-only cutover operation.

The stable Ingress and OAuth2 Proxy boundary is suitable to retain: the portal Ingress already sends the unchanged hostname to `Service/platform-portal-private`, and its external-auth annotations use the stable OAuth Service and callback. It is not safe to add a second Deployment without first resolving the RWO `/data` mount, isolating traffic reconciliation from the PreSync migration Job, consolidating NetworkPolicies, and replacing single-workload promotion/status/verification assumptions.

| Requested concern | Current implementation | Assessment |
|---|---|---|
| Stable Service selector switch | Service selects only `app: platform-portal-private`; no `slot` value exists | **Missing / P0** |
| Ingress and OAuth stability | Stable hostname, TLS secret, OAuth Service, auth URL, sign-in URL and callback already exist | **Reusable, but untested for slot switching** |
| Migrations | Candidate-image PreSync Job gates the single Application sync | **Good credential boundary; unsafe cutover coupling / P0** |
| RWO `/data` | Portal mounts `platform-portal-private-data` (`ReadWriteOnce`) at `/data` | **Blocks safe dual-slot scheduling / P0** |
| NetworkPolicies | Three overlapping portal ingress definitions, including a duplicate resource name | **Must consolidate / P1** |
| Image consistency | Portal, migration and collector currently share one SHA tag; promotion updates all three | **Consistent today, not slot-aware** |
| Expand/contract DB policy | Compatibility is prose only; no automated old/new-version compatibility gate | **Insufficient / P0** |
| Preflight | General tests and post-promotion checks exist; no inactive-slot or `/data` preflight | **Insufficient / P0** |
| Rollback | Generic Git image revert; no stable-selector rollback | **Missing for blue/green / P0** |
| Verification | Verifies one Deployment, first matching pod, DB CLI and OAuth redirect | **Not slot-aware / P0** |

## Current reconciliation and traffic path

```text
Argo Application/platform-portal-private
  path: private-platform-manifests/ (automated prune + self-heal)
    PreSync migration/seed/DB verification Job
    Deployment/platform-portal-private (one replica)
    Service/platform-portal-private (selector: app only)
    stable portal Ingress + OAuth Ingress/Deployment/Service
    storage, status collector, Redis and NetworkPolicies

platform.traditionalstrength.co.uk
  -> nginx external auth -> Service/platform-oauth2-proxy
  -> Ingress/platform-portal-private
  -> Service/platform-portal-private
  -> the single portal Deployment
```

Because traffic, workload and migration resources share one Application/path, a future selector-only desired-state change in this directory would create an Application sync whose PreSync phase includes the migration Job. A traffic cutover therefore is not demonstrably migration-free. Sync waves do not solve this: they order resources inside a sync, whereas the required boundary is separate reconciliation ownership.

## Findings

### P0 — no stable selector-only traffic switch exists

Evidence: `private-platform-manifests/private-platform.yaml` defines one Deployment and a Service whose only selector is `app: platform-portal-private`. Deployment and pod labels have no slot identity. The workflow and `scripts/gitops/promote_image.py` update the existing workload in place.

Required target:

- fixed `platform-portal-private-blue` and `platform-portal-private-green` Deployments with immutable selectors containing common application/component labels and exactly one `slot: blue|green`;
- internal Blue and Green Services for direct validation;
- the existing `Service/platform-portal-private` retained as the public traffic boundary, selecting common labels plus exactly one slot;
- one cutover commit whose only semantic change is the stable Service's slot value; and
- no public per-slot Ingress and no second OAuth callback.

Kubernetes Service selector changes are not transactional with application readiness. The cutover procedure must first prove the candidate direct Service ready, then change Git, then prove EndpointSlices contain only ready pods from the chosen slot. An ambiguous, absent, or unsupported slot selector is a failed state.

### P0 — migration execution and traffic switching share an Argo boundary

Evidence: `argocd-applications/platform-portal-private.yaml` points to the entire `private-platform-manifests` directory. The generated-name Job in `private-platform.yaml` is an Argo `PreSync` hook and runs `flask db upgrade`, both seed commands, and `flask verify-production-db`. Automated prune and self-heal are enabled.

Positive controls already present are worth preserving: `backoffLimit: 0`, a 600-second deadline, candidate application image, separate migration credentials, a read-only root filesystem, no service-account token, and post-migration database verification. The long-lived portal receives only the runtime DB Secret.

The release and traffic resources must be split into separate Argo Applications/paths. The release Application owns both slot workloads, direct Services, migration, OAuth, status and policies. A traffic Application owns only the stable Service and Ingresses and must contain no Job or hook annotation. Promotion changes the inactive slot and deterministic candidate Job; cutover changes only the stable selector. Resource ownership must be unique during the split so automated pruning cannot delete an object being transferred.

### P0 — the RWO `/data` mount is incompatible with unconstrained dual-slot placement

Evidence: `PersistentVolumeClaim/platform-portal-private-data` requests `ReadWriteOnce`, and the portal mounts it read/write at `/data`. The Deployment also mounts the distinct RWX `platform-status-snapshots` claim read-only at `/status`. The migration Job does not mount `/data`.

Repository tracing supports removal, but cannot prove live-volume contents:

- production `DATABASE_URL` comes from `flask-runtime-secrets` and the application normalizes PostgreSQL URIs;
- immutable bundled content is copied to `/app/data`, not `/data`;
- the only portal runtime `/data` dependency found is the manifest mount and stale generic wording in `portal/database_config.py`; and
- platform status intentionally uses the separate Azure Files RWX claim.

RWO permits attachment to one node, not safe independent placement of two slots. Co-scheduling may appear to work and then fail after rescheduling or node loss. Do not solve this with slot-local databases or an unexplained RWX conversion. Before removal, an separately authorized read-only live preflight must confirm the DB scheme without printing the URL, inspect mounts/open-file metadata, and inventory `/data` names, sizes, ownership and hashes without reading sensitive contents. Stop if a writer or unexplained state exists. Then remove `/data` from both slot pods, retain the unmounted PVC through the rollback window, and delete it only in a later approved change.

The Redis RWO `/data` in `redis-session-store.yaml` is a separate stateful concern. It does not mount into portal slots and does not itself block dual portal Deployments, but Redis availability and session continuity still require verification across cutover.

### P0 — database compatibility is not an enforceable expand/migrate/contract policy

The operations guide says migrations must remain compatible with the previous image, but CI only checks one migration head and exercises migrations/tests. No release gate boots or tests both the retained and candidate application versions against the post-migration schema. Existing migrations have downgrade functions, but incident response must not assume that destructive downgrades are safe.

Required policy:

1. **Expand:** add nullable columns, new tables/indexes or dual-readable structures before candidate code depends on them. Avoid destructive renames, drops, incompatible type changes and new mandatory writes.
2. **Migrate/backfill:** use bounded, resumable, observable and idempotent work. Do not hide a long backfill inside the cutover. Both old and new applications must operate against the resulting schema.
3. **Contract:** remove old structures only in a later release after the former slot and rollback window are deliberately retired. Contract migrations require separate review and backup/restore evidence.

Rehearse against a sanitized production-shaped PostgreSQL backup: old image before and after expansion, candidate after migration, seeds twice, concurrent representative reads/writes, lock/duration bounds, and exact Alembic head. If the retained slot cannot run after migration, cutover is forbidden. Database incident recovery is selector rollback plus forward-fix; Alembic downgrade or database restore is a separately authorized data operation.

### P1 — ingress and OAuth identities are stable, but their invariants are not guarded

Evidence: both Ingresses retain `platform.traditionalstrength.co.uk` and `platform-traditionalstrength-tls`; `/oauth2` targets the stable OAuth Service; `/` targets the stable portal Service; the external auth URL uses the OAuth Service DNS name; and oauth2-proxy declares the fixed callback `https://platform.traditionalstrength.co.uk/oauth2/callback`.

These objects should remain behaviorally unchanged during slot creation and cutover. CI needs golden assertions for hostname, TLS secret, ingress class, `/oauth2` backend, portal stable backend, auth URL/sign-in/response headers, cookie name and redirect URL. Candidate validation should use an internal direct Service, not a public Green host that would expand the OAuth redirect and certificate surface.

The current edge check proves only that an anonymous `/health` request receives HTTP 302. It does not prove the redirect destination, callback success, session continuity, authenticated identity headers, or an authenticated application journey. Those are required after cutover and rollback.

### P1 — NetworkPolicy ownership is overlapping and drift-prone

Three manifests allow portal ingress:

- `networkpolicy.yaml` selects both portal and OAuth pods and opens both ports to both ingress-nginx and production;
- `networkpolicies.yaml` separately selects the portal and allows the same two namespaces; and
- `allow-private-portal-from-nginx.yaml` declares the same `allow-private-portal-from-nginx` object name again with equivalent split rules.

Directory reconciliation therefore includes two desired documents with the same `(apiVersion, kind, namespace, name)` and a third overlapping policy. Additive NetworkPolicy semantics may keep traffic working, but ownership, diffs and test intent are ambiguous. Replace them atomically with one OAuth rule, one slot-neutral portal rule selecting common application/component labels and covering both slots, and the separate ACME rule. Preserve ingress-nginx and only the narrowly justified production callers. Add explicit egress policy if the namespace does not already provide it; the current private manifests do not define a portal default-deny egress or required DNS/PostgreSQL/telemetry rules.

Disposable-cluster tests must prove ingress-nginx and approved production probes are allowed to both direct slot Services, unrelated namespaces are denied, OAuth remains reachable from nginx, and database/DNS egress matches the selected CNI's NetworkPolicy behavior.

### P1 — image consistency is single-release consistency, not blue/green identity

At the audit base, the portal Deployment, migration Job and status collector all reference `platform-portal-private:4b55baf61e1b80464c79e75c9f793da7ea3f2bc7`. The promotion script expects and replaces exactly those three references, and the workflow builds/pushes a full Git-SHA tag. This avoids accidental application/migration code skew in the current release.

For blue/green, promotion must update only the inactive Deployment and candidate migration Job. It must not overwrite the active slot, stable Service or Ingress/OAuth resources. The collector image should change only when its code contract requires it; its reported slot images must come from Kubernetes state, not its own image. Prefer registry digests or prove tag immutability and record resolved digests. The version-tagged OAuth image and `redis:7-alpine` are not digest-pinned and must never be silently changed as part of an application cutover.

Promotion must be YAML-aware and fail on a missing/duplicate resource, mutable application reference, active target, selector ambiguity, inconsistent candidate Deployment/Job image, or any traffic-path diff. The current global regex replacement cannot express these rules.

### P1 — status, preflight and verification assume one workload

Evidence:

- the collector names one `STATUS_DEPLOYMENT`, one app label, one Service and one health URL;
- collector RBAC permits `get` on deployments but the data model has no per-slot or active-selector state;
- the workflow verifies one Deployment and selects `.items[0]` from the broad app label;
- `tools/verify-private-platform.sh` checks one rollout and still requires the RWO PVC; and
- validation counts image strings but does not render or assert a blue/green topology.

The collector and UI must expose the stable selector's active slot plus independent desired/ready counts, exact images/digests, restarts and direct health for Blue and Green. It must fail closed on malformed selector state. Verification must address named resources and compare exact images; never infer active traffic from newest image or the first pod returned.

## Required preflight and release gates

No live action is authorized by this review. Before any later approved implementation or cutover, require the following evidence.

### Repository and disposable-environment gate

- Strictly render/validate both release and traffic paths and both Argo Applications.
- Assert exactly two fixed slot Deployments and direct Services, immutable slot selectors, one stable Service selecting exactly one slot, and no public slot Ingress.
- Assert unique ownership of every namespaced resource and no Job/hook in the traffic path.
- Assert candidate promotion changes inactive Deployment + candidate Job only; cutover changes the one stable selector scalar only.
- Assert portal slots do not mount `/data`; migration Secret is only in the Job; runtime Secret is in both web pods.
- Validate one Alembic head, upgrade from production-shaped data, seed idempotence, and old/new compatibility after migration.
- Exercise NetworkPolicies and Blue-direct, Green-direct, stable-Service and double-switch routing in a disposable namespace.
- Test status schema, malformed selectors, unavailable slot, partial readiness and exact EndpointSlice membership.

### Separately authorized live read-only preflight

- Record Argo revision/sync/health and ensure no unexpected resource ownership warning.
- Capture the stable Service selector and EndpointSlices; confirm the currently serving pod image digest.
- Complete the sanitized `/data` inventory and open-writer check described above.
- Confirm runtime DB uses an approved PostgreSQL scheme and migration/runtime Secret boundaries without printing values.
- Confirm current Alembic head, PostgreSQL backup/PITR status, restore owner, migration lock/duration budget and forward-fix owner.
- Record ingress host/TLS/backend/auth annotations, certificate readiness, OAuth ping, anonymous redirect target, authenticated callback/session and a representative authorized application journey.
- Record baseline availability, latency, 4xx/5xx, pod restarts, DB errors and Redis/session behavior.

Any unexplained `/data` use, incompatible schema, failed backup gate, ambiguous selector, image mismatch, duplicate ownership, failed direct health, or unproven authenticated path is a stop condition.

## Candidate release, cutover and rollback contract

1. Read the active slot from the Git stable-Service selector; require exactly `blue` or `green`. The other fixed slot is the only valid candidate.
2. Promote the immutable candidate image to the inactive Deployment and deterministic migration Job in one release commit. Keep the active slot unchanged.
3. Reconcile only the release Application. Require successful migration/seeds/DB verification, exact candidate digest, full candidate readiness, direct-Service health, DB compatibility, authenticated smoke, acceptable logs/restarts and stable old-slot health.
4. Obtain production approval. Generate a cutover commit whose diff contains only the stable Service slot value. Reconcile only the traffic Application.
5. Verify EndpointSlices contain only ready candidate-slot addresses, stable internal health, unchanged ingress/OAuth invariants, anonymous redirect, authenticated callback/session and representative read/write behavior. Observe error/latency/DB/session signals.
6. Keep the previous slot at its exact image and replica count for the defined rollback window. Do not promote over it or run a contract migration.
7. Roll back with a reviewed Git commit changing only the stable selector to the previous slot. Do not use `kubectl patch` as the normal procedure because Argo self-heal would restore Git state.
8. Repeat endpoint, external auth, application, database and session verification after rollback. Forward-fix the database. A downgrade/restore requires its own incident authority and recovery plan.

Service switching cannot rescue an ingress, OAuth, database, shared-session or cluster-wide failure. Those failure domains need their existing recovery procedures. If migration fails, abandon the candidate while traffic remains on the active slot. If cutover verification fails and the old slot remains schema-compatible and healthy, switch the selector back immediately through Git.

## Implementation sequence and acceptance decision

1. Build offline contracts/tests and a YAML-aware promote/switch tool.
2. Consolidate NetworkPolicies and prove unique resource ownership.
3. Split release and traffic Argo ownership without duplicate or pruned resources.
4. After the authorized `/data` preflight, remove the mount while retaining the claim.
5. Introduce Blue and Green on the same known-good image; keep stable traffic on the incumbent slot.
6. Validate both direct Services and status schema, then rehearse candidate promotion, selector cutover and selector rollback in a disposable environment.
7. Only after all gates pass, submit a separately authorized production change plan.

Acceptance criteria are repository-testable and binary: two healthy fixed slots; stable selector exactly one slot; unchanged stable ingress/OAuth identities; traffic path contains no hook; inactive-only immutable promotion; old/new DB compatibility; no portal `/data` dependency; slot-neutral tested policies; exact endpoint/image verification; and a proven selector-only rollback.

Until those criteria are met, the current implementation remains a migration-gated rolling deployment, not blue/green.

## Audit method and limitations

The audit used static inspection and cross-reference tracing at base `7d77bdc`. The checkout HEAD differs from that base only by the task prompt file, which is not implementation state. No Kubernetes, Argo CD, Azure, registry, DNS, OAuth provider, PostgreSQL or production endpoint was queried; no existing manifest, workflow, migration or runtime file was changed. Repository evidence cannot establish live PVC contents, active endpoints, deployed image digests, actual Argo ownership, OAuth callback success, backup usability, CNI policy enforcement or database compatibility under production load.
