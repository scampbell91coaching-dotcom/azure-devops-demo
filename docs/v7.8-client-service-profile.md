# V7.8 client service profile

## Decision

`ClientServiceProfile` is the platform-owned source of truth for coaching service
access. Billing is not queried when access is decided. A future billing adapter
may propose or write a new profile revision with `billing_sync` provenance, but
the resulting platform record remains the entitlement decision.

The first implementation is a schema-independent domain and repository seam in
`platform-portal/portal/services/client_service_profiles.py`. No route is gated
in this change because there is not yet durable profile storage; partially
enforcing an in-memory policy would create inconsistent access.

## Existing model review

- `Athlete` owns identity, lifecycle status, competition metadata and coach
  notes. None of those fields express purchased/enabled services.
- `User` owns login role and account activation. `active` means the login works;
  it is not a coaching-package entitlement.
- `AthleteCheckinSettings.training_enabled` and `nutrition_enabled` choose the
  modules in the weekly check-in workflow. They must remain workflow settings.
  In particular, `nutrition_enabled=False` does not currently disable standalone
  nutrition check-ins or nutrition imports.
- `WeeklyCheckin.training_included` and `nutrition_included` are historical
  snapshots of a submitted check-in. They must not be used for current access.
- Nutrition check-ins/imports, programming blocks/session logs, and meet entries
  are historical operational records. Disabling a service must not delete, hide,
  or reinterpret them.
- The exercise catalogue's `video_url` and an applicant's
  `video_feedback_ready` answer are unrelated to a video-review entitlement.

## Domain contract

A profile explicitly contains:

- training coaching enabled: boolean;
- nutrition coaching enabled: boolean;
- meet-day support enabled: boolean;
- video review: `none`, `limited`, or `included`;
- `effective_from` and optional `effective_until`;
- provenance; and
- an optional dated coach override with actor and reason.

Training and nutrition booleans are independent, so training-only,
nutrition-only, both, and neither are valid. Video review is not collapsed into
a boolean because `limited` must remain distinguishable from `included`.

## Defaults

Until an athlete has a persisted profile, resolution returns a synthetic
`legacy_default` profile:

| Service | Default | Reason |
| --- | --- | --- |
| Training coaching | enabled | Existing athlete programme access remains available. |
| Nutrition coaching | enabled | Existing standalone check-ins/imports remain available regardless of weekly check-in settings. |
| Meet-day support | enabled | Existing coach meet-day operations remain available. |
| Video review | none | No current video-review service surface exists. |

This fallback is a compatibility rule, not a row silently inferred from billing.
New-client creation should write an explicit profile once persistence exists.

## Effective-date semantics

Periods are half-open: `effective_from <= day < effective_until`. A null
`effective_until` means no scheduled end. Thus one revision can end on the same
date its replacement begins without ambiguity.

When multiple stored rows are effective, the row with the latest
`effective_from` wins. A later `recorded_at` wins a same-day tie, allowing a
correction to be appended rather than overwriting history.

A coach override is a partial replacement. Only non-null override values replace
base values, only during the override's own half-open period. It requires an
actor, reason, at least one changed entitlement, and `coach_override`
provenance. When it expires, base values resume. The stored base and override
remain unchanged.

## Access and historical data

`may_start_service` answers whether current/new service activity is permitted.
It deliberately does not offer a “may read history” decision. Existing
programmes, completed sessions, check-ins, nutrition data, meet records and
coach responses remain readable under their existing authorization rules after
an entitlement is disabled.

Route integration should distinguish operations:

- Gate creation, submission, import, assignment, and current-service workflows.
- Do not gate historical detail/list reads merely because today's entitlement is
  disabled.
- Keep authentication/athlete ownership and coach authorization checks in
  addition to entitlement checks.

## Persistence required before enforcement

A migration is intentionally deferred. The persistence adapter should add an
append-only `client_service_profiles` table (and preferably a separate
`client_service_profile_overrides` table) rather than columns on `athletes` or
check-in settings.

Minimum profile columns are: id, athlete foreign key, the three booleans, video
review value, effective-from, nullable effective-until, provenance,
provenance-reference or note, recorded-at, and recorded-by. Override rows need a
profile foreign key, nullable replacement values, effective dates, actor,
reason, provenance and recorded-at. Database checks should constrain enum
values, require end after start, and require at least one override value.

Rows should not be deleted or updated to reflect plan changes. Append a new
revision or bounded override. Foreign keys may cascade only when the athlete is
actually deleted under the platform's data-retention policy; disabling a
service is never deletion. Index `(athlete_id, effective_from,
effective_until)` for resolution. The adapter must return every candidate row
for `ClientServiceProfileService` and normalize stored timestamps consistently.

Before enabling route gates, backfill explicit profiles for existing athletes
using the documented legacy defaults, add repository integration tests against
SQLite and PostgreSQL, and deploy the read path before any write/admin UI.

## Out of scope

No billing provider integration, UI, route enforcement, migration,
infrastructure, or GitOps change is included in this slice.
