# V7.9 nutrition UX

## Outcome

V7.9 should present nutrition as four related but distinct records:

1. **Targets** — what the coach prescribed.
2. **Meal plan** — an optional, assigned way to meet those targets.
3. **Intake** — what the athlete actually consumed or imported.
4. **Check-in** — the athlete's retrospective adherence and context, plus the coach's review.

Bodyweight is a dated outcome signal, not intake or adherence. History preserves the version that applied on each date. These distinctions must appear in headings, field labels, empty states, source labels, and comparisons—not only in help text.

This document defines presentation and workflow. It does not authorize persistence, migrations, new routes, inferred adherence, or automated nutrition decisions.

## Audit of the current product

### Live coach surfaces

| Surface | What it currently shows | V7.9 risk or gap |
| --- | --- | --- |
| Coach **Nutrition** overview | Latest dedicated or weekly check-in calories, protein, self-rated adherence, recent check-in bodyweights, and source/date | Correctly says “Recorded check-ins only,” but “Nutrition” is too broad; it has no targets or assignments and “logged” can sound like daily intake. Disabled athletes remain mixed into a reporting overview without a per-card history-only state. |
| Athlete record | Imported seven-day aggregates, nutrition check-in history, copied target/average pairs, bodyweight, adherence, review status, and coach response | The page mixes imported actuals, self-reported averages, copied legacy targets, and review in one long record. The “Add nutrition check-in” coach action also suggests the coach is the reporter. |
| Daily review queue | Unreviewed dedicated nutrition check-ins when nutrition coaching is enabled | This is review work, not a target or meal-plan workflow. Disabled history is correctly excluded. |
| Check-in settings / client services | Weekly nutrition module and current nutrition-coaching access | Workflow configuration and entitlement are different concepts. Neither is a prescription state. |

### Live athlete surfaces

| Surface | What it currently shows | V7.9 risk or gap |
| --- | --- | --- |
| Dashboard **Nutrition & bodyweight** | Latest dedicated check-in averages, bodyweight, history, coach-response state, and trends | “Latest update” does not say whether values are targets or actuals. There is no current target or meal-plan status. |
| Dedicated nutrition check-in | Athlete enters both “coach-set target” and actual weekly average, plus adherence/wellbeing | This duplicates the prescription and makes an athlete-entered copy look authoritative. Training/rest variants cannot be represented. Until persistence changes, these fields must be labelled **reported target (legacy snapshot)** wherever read. |
| Weekly check-in nutrition module | Manual/imported averages, source/period, adherence, notes | It is evidence for review, not a prescription. Imported prefill remains a snapshot at submission. |
| MyFitnessPal import | Consent, preview/commit, daily aggregate actuals, completeness, and deletion | It correctly represents actual data, but coverage/partial status must travel with every comparison. Daily totals cannot prove that an assigned meal was followed. |

### V7.9-ready foundations

`portal.services.nutrition_prescriptions` already provides schema-independent coach-authored daily targets, optional training/rest overrides with daily fallback, inclusive effective dates, provenance, conflict detection, and immutable historical intent. It deliberately contains no actual intake or adherence.

`portal.services.meal_plans` already provides schema-independent fixed, flexible, and hybrid days; coach-curated food snapshots; ordered meals; target reconciliation and visible tolerances; substitutions; and reasoned overrides. It deliberately has no live assignment persistence or routes.

The foundations establish the correct boundaries, but they are not live product data. No screen may claim “Current targets” or “Meal plan assigned” until an authorized adapter can resolve a real prescription/assignment for that athlete and date.

## Canonical language

| Concept | Primary label | Supporting copy | Do not use as a synonym |
| --- | --- | --- | --- |
| Coach prescription | **Current targets** | “Set by Coach Name · effective 12 Aug 2026” | plan, intake, logged, adherence |
| Variant | **Training-day targets** / **Rest-day targets** | “Daily targets apply when no variant is set” | high/low day without definition |
| Assigned food structure | **Meal plan** | “Assigned 12 Aug · Fixed / Flexible / Hybrid” | targets, diet, food log |
| Consumed nutrition | **Actual intake** | “Imported from MyFitnessPal” or “Reported in check-in” | targets, plan, adherence |
| Data completeness | **Coverage** | “5 of 7 days present · 4 complete” | compliance, adherence |
| Athlete reflection | **Nutrition check-in** | “Self-rated adherence 7/10” | intake log, target |
| Coach task state | **Needs review** / **Reviewed** | Include submitted/reviewed date | compliant / non-compliant |
| Outcome | **Bodyweight trend** | Dated values with source | adherence |
| Previous prescribed state | **Target history** / **Meal-plan history** | Immutable effective dates and author | old data, latest target |
| Disabled service | **Nutrition coaching ended** and **History only** | “No new targets, plans, imports, check-ins, or reviews can be added.” | inactive data, deleted |

Use **calories**, **protein**, **carbohydrate**, **fat**, and **fibre** consistently. “Carbs” is acceptable only in dense athlete-facing metric labels, never alongside “carbohydrate” on the same screen. Every actual value must carry a source and period/date. Every prescribed value must carry an effective date and author/provenance.

## Information architecture

### Coach athlete nutrition workspace

Use one athlete-scoped **Nutrition** workspace with stable tabs or same-page landmarks in this order:

1. **Overview** — current target status, meal-plan assignment status, actual-intake coverage, latest bodyweight trend, and check-in review state.
2. **Targets** — current resolved prescription, training/rest variants, effective dates, notes, and create-revision action.
3. **Meal plan** — current/scheduled assignment and reconciliation; assignment is optional and visibly subordinate to its target snapshot.
4. **Intake** — daily actuals, source, coverage and missing/partial days; never presents unknown days as zero.
5. **Check-ins** — athlete-reported adherence/context and coach review/response.
6. **History** — dated target revisions and meal-plan assignments, with links to the check-ins/intake evidence from the same period.

The cross-athlete coach **Nutrition** page remains a triage/reporting index. Its cards should show separate rows for **Target**, **Meal plan**, **Intake coverage**, and **Check-in review**, each with a state and exact deep link. Do not calculate one overall “nutrition status.”

### Athlete nutrition workspace

Use one athlete **Nutrition** destination with this reading order:

1. **Today’s targets** — resolved for today's date and known day type.
2. **Today’s meal plan** — only when assigned; otherwise clearly say targets can exist without a meal plan.
3. **Record / import actual intake** — source and coverage controls.
4. **Check in** — due state and the last coach response.
5. **Progress** — bodyweight and intake-versus-target comparisons with adequate coverage.
6. **History** — previous prescriptions, assignments, submissions, and responses.

Training remains the primary dashboard action for combined coaching. The nutrition card should summarize, not reproduce, this workspace.

## Workflow definitions

### 1. Current targets

Coach workflow: open **Targets**, review the current effective prescription, then choose **Create target revision**. The confirmation view shows all macro values, author, effective-from date, optional end date, notes, and whether an existing period would be closed. Editing never rewrites a prior effective period.

Athlete view: heading **Today’s targets**, day label, macro values, “Set by …,” and effective date. If no prescription resolves, show **No targets assigned** and “Your coach has not assigned nutrition targets for this date.” Do not fall back to copied check-in targets.

### 2. Training/rest variants

The coach starts with **Same targets every day**. Turning on **Different training and rest days** reveals both named groups while retaining **Daily targets** as the explicit fallback. Preview must state which target set applies to each upcoming date and why.

The athlete sees one resolved set first, labelled **Training day**, **Rest day**, or **Daily targets**. A secondary **View all target variants** disclosure shows the other sets. If day classification is unknown, show daily targets and “Day type not set”; never guess from a completed workout or calendar proximity.

### 3. Meal-plan assignment

A meal plan is optional. Coach flow is **Choose published template revision → select athlete/effective dates → reconcile each day with the target snapshot → preview → assign**. Out-of-tolerance fields are named with target, planned total, signed delta and tolerance. A reasoned coach override remains visible.

The athlete sees assignment name/revision, effective dates, day mode, ordered meals/portions, fixed and flexible allocations, permitted substitutions, and assigned target versus planned total. **Assigned meal plan** never replaces **Current targets** as the source of prescribed macros.

Empty states distinguish **No meal plan assigned** from **Meal plan starts on DATE**, **Meal plan ended**, and **Meal plan unavailable because no target snapshot exists**.

### 4. Actual intake

Every intake presentation includes:

- source: imported provider or athlete-reported check-in;
- period: exact day or check-in date range;
- coverage: present/expected days and complete/partial/missing counts;
- freshness: recorded/imported timestamp;
- values explicitly labelled **Actual** or **Reported average**.

Imported daily values and check-in averages remain separate records even when dates overlap. The UI may compare them but may not silently merge, prefer, or deduplicate them. Missing is **Not recorded**, never `0`. Imported daily totals may support target comparison, but cannot establish meal-plan completion.

### 5. Bodyweight trend

Show bodyweight in its own chart/list with date, value, and source available per point. The default coach view uses a rolling trend only when the method and sample coverage can be stated; otherwise show dated points. Avoid a single change number without its comparison dates.

Profile bodyweight has no observation date and must be labelled **Profile bodyweight · date not recorded**. Check-in and imported bodyweights must not be collapsed on the same date without a visible source rule. No target-range, weight-class judgement, or causal nutrition claim is inferred.

### 6. Adherence and review

Keep three signals separate:

- **Self-rated adherence** — the athlete's 1–10 answer and context.
- **Meal-plan completion** — followed / partly followed / not followed / not applicable, only when an assignment and adherence event exist.
- **Intake versus target** — arithmetic comparison, only for known target dates with sufficient actual coverage.

The coach review header shows submission period, source/coverage, applicable target revision, applicable meal-plan assignment, bodyweight context, athlete notes, and prior response. Its task state is **Needs review** or **Reviewed**. Reviewing records a response/status; it does not alter targets. The adjustment path is **Create target revision** or **Revise meal plan**, with a review-to-change link and reason, never inline mutation of history.

### 7. History

History is effective-dated, newest first, and filterable by **Targets**, **Meal plans**, **Intake**, and **Check-ins**. Each prescription row shows effective interval, variants, author and revision/source. Each assignment row shows template revision, target snapshot, effective interval, lifecycle state and override marker.

Opening a historical check-in resolves the prescription/assignment that applied to that check-in period and labels legacy athlete-copied target fields **Reported target (legacy snapshot)**. It must not display today's targets beside old actuals without an explicit “current, not applicable to this period” warning.

### 8. Disabled-entitlement historical-read state

When nutrition coaching is disabled:

- athlete nutrition navigation, cards, prompts, direct entry/import routes, and nutrition-derived dashboard projections remain absent or rejected under the established authorization policy;
- the coach athlete workspace begins with a persistent **Nutrition coaching ended · History only** banner containing the effective end date when known;
- coach history retains targets, meal-plan assignments, intake/import summaries, check-ins, bodyweight points, reviews, and provenance;
- all mutation controls are absent: no assign, revise, import, disconnect/delete, submit, respond, mark reviewed, substitute, or adherence action;
- pending review items are removed from active queues and shown in history as **Unreviewed when coaching ended**, not “Needs review”;
- scheduled future prescriptions/assignments are labelled **Did not become active** if entitlement ended first; they must not look current;
- re-enabling coaching does not silently reactivate ended prescriptions or assignments. The coach must explicitly confirm or create a current revision.

The banner must explain retained data without implying deletion: “Past nutrition records are retained for reference. Enable nutrition coaching before assigning new targets or plans, importing intake, or reviewing check-ins.”

## State model and comparison rules

| Object | Current/scheduled states shown in UI | Empty/exception states |
| --- | --- | --- |
| Target prescription | Current, Starts DATE, Ends DATE | No targets assigned, Gap in targets, Conflicting data (do not resolve) |
| Meal-plan assignment | Draft (coach only), Scheduled, Active, Superseded, Ended | No meal plan assigned, Reconciliation required, Override |
| Actual intake | Imported, Reported, Complete, Partial | Missing / Not recorded, Import failed |
| Check-in | Due, Submitted, Needs review, Reviewed | Not scheduled, Overdue, Unreviewed when coaching ended |
| Entitlement | Nutrition coaching active | Nutrition coaching ended · History only |

Comparisons must join records by athlete and date, preserve both source IDs/revisions, and show coverage. A target-versus-actual percentage is not shown when the target is absent/ambiguous, the actual period is absent, or period coverage is below an agreed policy threshold. V7.9 UX does not define that threshold; until product policy does, show raw values and coverage without a percentage or adherence classification.

## Responsive acceptance criteria

The criteria apply to coach and athlete Nutrition overview, Targets, Meal plan, Intake, Check-ins, History, and history-only states. Test with representative long athlete/template names, all five macro fields, an override, missing data, and 200% browser zoom.

### Desktop (1280 px viewport and above)

1. The page title and active/history-only state are visible without scrolling; primary content remains athlete-scoped.
2. Overview shows separate Target, Meal plan, Intake coverage, Bodyweight, and Check-in review regions. No card combines prescribed and actual values without **Target** and **Actual** column headings.
3. Target/actual comparison uses a table with metric, target, actual, delta, and source/coverage context. Signed deltas are text, not colour alone.
4. Training/rest variants can be compared side by side, while the currently resolved variant has both a text label and a non-colour indicator.
5. Meal order, fixed subtotal, flexible allowance, planned total, target and reconciliation remain visually nested. Template revision and effective interval stay in the assignment header.
6. Bodyweight points expose date/value/source via visible list/table or keyboard-accessible chart equivalent; the chart is never the only representation.
7. History filters and row actions are keyboard operable with a visible focus indicator; deep links land on the exact revision/submission.
8. A history-only banner spans the content column and all mutation controls are absent, not merely disabled.

### 430 px

1. There is no horizontal page overflow at 430 CSS px; navigation, banners, cards, dialogs and validation summaries fit the viewport.
2. Overview regions form one column in the canonical reading order. The resolved target and day type appear before any actual-intake value.
3. Macro comparison converts to labelled stacked rows/cards or uses a focusable, explicitly labelled scroll region; target/actual/source labels remain visible for every value.
4. Training/rest variants use a select/disclosure or stacked groups, not squeezed columns. Switching the visible variant does not change stored data.
5. Meal items wrap their name, portion and substitution action; no food name or unit forces overflow. Fixed and flexible sections retain headings.
6. Primary actions are at least 44 by 44 CSS px, do not overlap sticky navigation/safe areas, and use full available width where appropriate.
7. Source, period, coverage and partial/missing state remain visible; they are not removed as “secondary” mobile content.
8. The history-only banner precedes records and no mutation button appears in menus or overflow controls.

### 390 px

All 430 px criteria apply, plus:

1. Five macro values stack without clipped units or numeric values; labels may wrap to two lines.
2. Target metadata (day type, author, effective date) remains adjacent to the target group, before meal plan or intake.
3. History rows become cards with type, effective/submission date, state, and one descriptive link; filters wrap without horizontal scrolling.
4. Bodyweight history shows a readable dated list when the graph cannot preserve labels.
5. Form errors appear in a focused summary and beside the field while preserving entered values; numeric controls use appropriate input modes and at least 16 px text.

### 320 px

All 390 px criteria apply, plus:

1. The page has no horizontal overflow at 320 CSS px with 200% zoom testing performed separately; content does not rely on a minimum card width greater than the viewport.
2. Header actions stack below the title. Only one visually primary action is presented per workflow step.
3. Macro values use `kcal` and `g` without truncation. Long numbers wrap or scale within their own value region rather than overlapping another metric.
4. Intake coverage reads as a sentence (for example, “5 of 7 days present; 4 complete”) instead of a dense multi-column tally.
5. Meal-plan reconciliation lists each outside-tolerance field vertically with target, planned and signed delta; override reason is fully readable.
6. Touch targets remain 44 by 44 CSS px with at least 8 px separation, visible keyboard focus, and no hover-only information.
7. Coach response, athlete notes, source provenance and history-only explanation are not truncated; disclosures have an accessible name and state.

### Shared semantic and accessibility checks

1. Heading order is logical and each landmark has a unique accessible name.
2. “Target,” “Actual intake,” “Coverage,” “Self-rated adherence,” and “Reviewed” are present as visible text; colour/icons never carry the distinction alone.
3. Dates include year in history and use the user's locale/timezone consistently; effective intervals state inclusive boundaries.
4. Empty, loading, error, conflict, partial, and history-only states do not show zero values as substitutes for unknown data.
5. Screen-reader output for every macro comparison includes metric name, target, actual, unit and coverage/source.
6. Focus moves to validation/conflict summaries after failed assignment/revision submission and returns predictably after dialogs.
7. Destructive import deletion remains a separately confirmed action only while entitled; it is absent in history-only mode.

## Sequenced implementation handoff

1. Agree persistence and authorization for prescriptions and assignments, including immutable revisions and entitlement end behavior.
2. Add read models that expose each record type separately; do not extend the current blended `NutritionRecord` into a universal model.
3. Deliver coach Targets and athlete read-only current targets before removing legacy copied target fields from check-ins.
4. Deliver meal-plan assignment/reconciliation and athlete plan view against immutable target snapshots.
5. Add explicit intake coverage and comparison policy, then consolidate duplicate dedicated/weekly nutrition capture based on observed use.
6. Add cross-linked review and history, including historical-read entitlement states.
7. Remove legacy target entry only through a separately reviewed migration/deprecation plan. Historical values remain labelled snapshots.

No template prototype is included in this audit. The current application has no live prescription or assignment view model; rendering invented target/assignment states would blur the exact boundary this UX is intended to protect.
