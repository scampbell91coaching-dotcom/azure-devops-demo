# V7.10 performance dashboard query contracts

## Scope

This audit covers the query, authorization, filtering, and incomplete-data seams
used by the V7.10 coach-facing athlete performance dashboard. It complements the
V7.9 query audit and defines integration contracts for the metric services.

## Contracts

- Every metric query must require an explicit athlete ID. Block IDs and date
  ranges narrow that scope; they never replace the athlete predicate.
- A requested block must belong to the requested athlete. Unknown and
  cross-athlete block IDs must produce the same not-found outcome and must not
  fall back to all-history data.
- Date windows use an inclusive start and inclusive end in the product contract.
  Services should implement the end safely for timestamp columns (for example,
  as a half-open interval ending at the next midnight).
- Empty or incomplete history remains empty/unknown. It must not contribute zero
  loads, zero RPE, missed reps, or fabricated trend points.
- Dashboard collection loading must be bounded by the selected block/date window
  and use aggregate or batched reads. Query count must not grow with sessions,
  sets, exercises, or unrelated athlete history.
- Deterministic decision summaries consume the same filtered metric snapshot
  shown to the coach and retain reason/evidence fields so each recommendation is
  explainable.

## Existing seam hardened

Athlete schedule projection previously loaded all of an athlete's session logs,
including archived blocks, before discarding irrelevant rows in memory. It now
joins through session and week and reads only logs for the active block. The log's
athlete predicate remains mandatory, preventing a malformed cross-athlete
session reference from crossing the authorization boundary. With no active block,
the service performs no log query.

Focused regression tests assert one SELECT for active-block logs regardless of
the amount of archived history, exclusion of archived and cross-athlete rows, and
zero log SELECTs when no active block exists.

## Integration risks to re-check

- Metric branches may choose different date-column semantics (`completed_at`,
  `started_at`, or check-in date). The integrated dashboard should expose one
  documented selection rule.
- A UI block selector must submit stable block IDs, while the service independently
  validates athlete ownership.
- Query-count assertions should be added around the final combined dashboard
  service after metric branches are integrated; fixed query count alone should be
  paired with bounded-row tests.
