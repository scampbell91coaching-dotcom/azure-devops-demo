# Traditional Strength V7.3 real-athlete-readiness audit

**Audit date:** 9 August 2026

**Baseline:** production declaration at `508af70` (V7.2 integration)

**Decision:** **NO-GO for unattended onboarding of an arbitrary real athlete tomorrow.** A tightly supervised pilot is possible only if the athlete can pass the Entra/OAuth2 edge, the coach uses the manual invitation link, supplies dates and warm-ups outside the structured product, and agrees an external contact/recovery channel. Those are operating conditions, not product readiness.

## Evidence standard and limits

- **Confirmed** means evidenced by current production manifests, application code, templates, migrations, or tests.
- **Operational verification required** means the repository declares a capability but this audit did not query the live cluster, mail provider, database, backup inventory, or DNS.
- **Coach/spreadsheet hypothesis** means plausible coaching need without a representative spreadsheet or coach observation session.

No coaching spreadsheet exists in this checkout. The V7.2 audit's spreadsheet-parity claims remain hypotheses. This audit was documentation-first: no migrations, runtime code, CI/CD, or production configuration were changed.

### Non-blocking friction for one supervised athlete

- Intake/application data does not convert into an athlete profile or confirmed programming state; the coach rekeys it.
- Athlete setup captures only basic identity, bodyweight/class, federation and a free-text competition field. Availability, equipment, training maxes, session cap and lift preferences are not first-class.
- Block Factory now has deterministic accessory suggestions, but coach pins and candidate selection still do not create a calendar-aware, whole-block coaching workspace.
- The athlete can save partial set progress, completed/skipped state, actual load/reps/RPE, extra sets and a 500-character set note. There is no skip/deviation reason, session readiness/RPE/duration, video/link, pain location/severity, or substitution request.
- Completed session logs are intentionally locked. The UI tells the athlete to ask the coach, but there is no correction/revision workflow.
- Check-ins and nutrition are usable but split across overlapping weekly and dedicated nutrition models/forms.
- Coach response exists inside weekly/nutrition check-ins, not as a conversation. There is no delivery, unread state, notification, or urgent escalation guarantee.
- The platform has no athlete self-service email/password change, account closure, data export, or deletion request workflow.

## Safe day-one operating runbook

If the coach chooses a supervised exception despite the no-go:

1. Confirm the athlete can pass the Entra edge in a clean private browser before creating/sending any token.
2. Create the athlete, confirm the email character-for-character, generate an invitation, inspect delivery state, and use the manual link only if required. Verify the link host is `platform.traditionalstrength.co.uk` and revoke/reissue after any accidental disclosure.
3. Create a draft programme. Put start date, dated week mapping, planned training days, missed-session rule, holiday/travel exceptions, and complete warm-up/ramp instructions in visible notes.
4. Coach previews on the athlete account at mobile width, activates only after review, and records an external copy of what was prescribed.
5. Athlete completes a non-critical test session while the coach is available. Confirm partial save, completion, athlete note visibility and check-in submission.
6. Agree one external contact channel, what counts as urgent, and that pain/injury is not diagnosed by the platform.
7. Coach checks every athlete page daily for completed logs and checks the review queue/check-in pages. Do not rely on alerts.
8. Before each material programme edit, record the old prescription and tell the athlete what changed. Do not edit completed-session history.
9. Give the athlete a manual route for correction, account closure and data-copy requests. Escalate database recovery rather than deleting records ad hoc.

## Confirmed gaps vs coach/spreadsheet hypotheses

### Confirmed gaps

- Edge authentication precedes app athlete authentication.
- Production-declared portal configuration lacks mail/base-URL settings.
- No calendar fields or holiday/travel exception model; current session is completion-order based.
- Training warm-up domain has no production integration.
- Completed session logs do not enter the coach action queue.
- No general messaging/notification path or session feedback state.
- No athlete data export, closure/deletion workflow, or completed-log correction path.
- No training-block/meet relationship.
- No active portal metrics/tracing/product telemetry in the application; monitoring definitions are disabled/proposed.
- Recovery is infrastructure-level, manual and untested for database restore; one replica and seven-day non-geo backup are declared.

### Coach/spreadsheet hypotheses requiring observation

- The coach needs a full block grid rather than a strong weekly review/edit surface.
- Exact warm-up taxonomy and whether warm-ups vary by athlete, lift, session, phase or reported readiness.
- Whether current spreadsheets calculate e1RM, tonnage, hard sets, fatigue or only display coach-authored targets.
- Which accessory slots, superset groupings and substitution hierarchies are actually reused.
- Which technical issues matter beyond the two encoded squat phrase rules and how the coach distinguishes cue, exercise, load and fatigue interventions.
- Whether video is essential every session, only for top sets, or handled acceptably via an external service.
- Desired holiday behaviour: pause calendar, slide sessions, compress week, prescribe travel alternatives, or simply record exceptions.
- Nutrition coaching scope, required trend windows, targets and whether MyFitnessPal imports are used in practice.
- Competition handoff fields and whether Meet Day is coach-only operations or part of the athlete product.

Validate these by shadowing one real programming setup, one training review, one weekly check-in response and one schedule disruption. Do not add generic schema or rules before that evidence.

## Over-engineered relative to real coaching use

1. **Intelligence ledgers outrun the loop.** Versioned facts, signals, recommendations, overrides, integrity checks and deterministic rules are sophisticated, while there is no normal UI for capturing technical observations or turning a candidate into an exact programme change and outcome.
2. **Warm-up abstraction outruns delivery.** Immutable protocols, applicability scopes, override provenance and repository seams are sound, but the athlete sees none of it. Persist and render the simplest coach-validated plan before extending matching logic.
3. **Accessory metadata outruns evidence.** Multi-field compatibility, phase/lift relevance, fatigue and priority can rank candidates, but basic schedule/equipment/availability capture is absent. Freeze metadata expansion until coach selections show which fields predict decisions.
4. **Multiple programming/template surfaces increase cognitive load.** Block Factory, older block-factory templates, programming engine APIs, hard-coded templates, database day templates and V7 routes coexist. Measure the one workflow the coach uses and retire/consolidate later.
5. **Six prescription modes outrun common editing.** The schema covers edge prescriptions, yet the coach lacks calendar state, bulk progression and revision communication. Avoid adding modes until usage is observed.
6. **Platform dashboards outrun athlete-journey telemetry.** Executive/engineering/security/history/release/observability surfaces are extensive, while the product cannot alert on a failed invite or unseen completed session.
7. **Two authentication layers add security and onboarding cost without a documented athlete identity design.** This may be appropriate for an internal portal, but the product now contains external athlete accounts. Resolve the boundary before layering more account features.

## Test and evidence result

- `python -m pytest -q` from `platform-portal`: **426 passed, 2 skipped in 42.22s**.
- The suite strongly supports domain correctness and authorization behaviour in a disposable SQLite environment.
- It does **not** establish live reachability, Entra eligibility, SMTP delivery, PostgreSQL browser behaviour, backup restoration, or real-athlete usability.

## Recommendation

Use the first athlete as a deliberately supervised discovery pilot, not a production-ready launch. Spend the next increment closing access/delivery, calendar/warm-up delivery, and review-loop visibility. Freeze new intelligence framework, taxonomy and SaaS-platform work until one coach and one athlete complete two real weeks and the confirmed friction is measured.
