# Traditional Strength V7.6: PWA and mobile readiness audit

**Status:** design/audit only  
**Audit date:** 10 August 2026  
**Scope:** current athlete web experience, installable PWA readiness, and a future Capacitor wrapper  
**Out of scope:** app-store submission, video implementation, Azure resource creation, production manifest/GitOps changes, and merging

## Executive decision

The athlete portal is a credible responsive-web baseline but is **not yet an installable PWA**. It has mobile-first athlete navigation, touch-sized training controls, secure cookie authentication, protected deep-link return after login, and automated coverage at 320, 390, and 430 pixels. It has no web app manifest, purpose-built icon/splash set, service worker, offline route, install/update UX, or athlete-facing JSON contract.

The safest progression is:

1. finish and measure the responsive web experience;
2. add installability while keeping all private responses network-only;
3. add a deliberately small offline session shell, only after its data classification and stale-write rules are agreed;
4. introduce same-origin athlete API seams that can serve both the PWA and a future Capacitor shell;
5. wrap the proven web experience in Capacitor and distribute a closed beta.

Do not build a broad cache-first PWA. Training prescriptions, completed sets, check-ins, nutrition, bodyweight, coach feedback, account pages, tokens, API responses, and authenticated HTML are sensitive and mutable. They must never enter a shared HTTP cache or an indiscriminate service-worker cache.

## Evidence and current state

This is a repository audit, not a production traffic or device-lab audit. Findings are based on the current Flask application, Jinja templates, static files, tests, and ingress definitions at commit `817dba5`.

### Mobile layouts

The athlete experience is server-rendered from `platform-portal/templates/athletes/` and uses `static/css/athlete_dashboard.css` plus `static/js/athlete.js`.

Current strengths:

- Every athlete base page has `width=device-width`, a dark `theme-color`, a skip link, semantic navigation, and a constrained content shell.
- The desktop navigation changes to a fixed five-item bottom navigation below 760 px. The session action area is sticky above that navigation.
- Inputs use suitable `inputmode` values; primary buttons and set controls are approximately 44–48 px or taller.
- The narrowest breakpoint below 360 px reduces padding, changes the three-column set input grid to two rows, and stacks sticky actions.
- `e2e/tests/mobile.spec.ts` checks athlete dashboard, programme and current-session surfaces at 320, 390, and 430 px, checks absence of horizontal overflow, and exercises a 430 px check-in form.

Gaps and risks:

- Automated tests establish layout fit, not real-device ergonomics, virtual-keyboard behavior, iOS safe areas, standalone-mode behavior, orientation, poor connectivity, screen-reader behavior, or dynamic text scaling.
- The bottom navigation and sticky session controls do not use `env(safe-area-inset-bottom)`; an iPhone home indicator can reduce usable space.
- There is no `viewport-fit=cover`, standalone-specific CSS, or installed-app title/status-bar metadata.
- The dashboard is long and information-dense. It fits a phone but needs observed-athlete usability testing for one-handed use during a session.
- JavaScript only enhances navigation state, add-set behavior, mutually exclusive completion/skipping, and finish confirmation. There is no draft persistence or reconnection state.

### Authentication and session behavior

`portal/__init__.py` and `portal/auth.py` provide the following current contract:

- Flask's default cryptographically signed client-side session cookie is used; no Flask-Session/Redis integration is configured for this app.
- Cookie flags are `Secure`, `HttpOnly`, and `SameSite=Lax`.
- The session is made permanent with an eight-hour lifetime, and `authenticated_at` is independently checked on every request. Expired sessions are cleared and the login page explains expiry.
- The cookie contains identifiers and CSRF state (`user_id`, `athlete_id`, timestamp, CSRF token), not athlete programme content. It is signed but not encrypted; no sensitive domain data should be added to it.
- Login rotates state with `session.clear()`. Logout is POST-only, CSRF-protected, and clears the session.
- Unsafe methods require a session-bound CSRF token. Athlete authorization is endpoint-allowlisted and athlete IDs are ownership-checked.
- An unauthenticated page request redirects to `/login?next=<same-origin path>`. The destination is repeatedly decoded and validated against open redirects before reuse. This already supports a link to `/athlete/programme/sessions/<id>` surviving login.
- API-shaped requests receive `401`; browser page requests receive a login redirect. There is no refresh-token, bearer-token, native SSO, or device credential contract.

Implications:

- An installed same-origin PWA can retain the existing cookie session exactly as the website does. It should treat an HTTP `401` or a redirect to login as authoritative and discard any private offline view.
- Eight hours is an absolute age from authentication, not a rolling offline entitlement. Offline availability must not silently extend it.
- A future Capacitor WebView may be able to use cookies, but cookie persistence, SameSite behavior, CSRF, universal/app links, and logout clearing must be proven on both iOS and Android. Do not assume browser behavior is identical.
- Prefer retaining cookie + CSRF authentication for the first Capacitor shell. Introduce native OAuth/OIDC tokens only as a separately threat-modelled identity project, not as incidental PWA work.

### Routes and rendering model

Core athlete routes are conventional Flask HTML/form flows:

| Flow | Current route(s) | Current behavior | Mobile direction |
|---|---|---|---|
| Sign in/account recovery | `/login`, `/account/<purpose>`, `/logout` | HTML form, cookie session, CSRF | Keep server-rendered; always online |
| Today/dashboard | `/athlete/dashboard` | Private HTML assembled from several domain services | Keep SSR initially; add a read API when Capacitor needs it |
| Programme | `/athlete/programme` | Private HTML | Keep SSR initially; candidate read API |
| Current session | `/athlete/programme/sessions/<id>` | GET HTML and atomic form POST | Keep SSR online; first domain to gain read/write APIs and guarded draft support |
| Check-ins | `/athlete/check-ins`, detail, and `/athletes/<id>/check-ins/new` | HTML GET/form POST | Keep SSR; later add own-user APIs |
| Nutrition check-in | `/athletes/<id>/nutrition-checkins/new` and POST | HTML form | Keep SSR; later add own-user APIs |
| Nutrition import | `/athletes/<id>/nutrition-import...` | multipart upload/preview/commit | Keep server-rendered and online-only |

Existing JSON endpoints are predominantly coach/platform operational endpoints under `/api/v1` and `/programming/api`. They are not a stable athlete mobile API. Reusing them would leak coach-oriented shapes and couple the mobile client to internal editing workflows.

### Static assets, manifest, and installability

Current state:

- No manifest link or manifest route/file exists.
- No service worker registration or worker exists.
- The only image asset is `traditional-strength-logo.png`: 1170×1675, RGB, about 651 KB. It is a portrait logo, not a complete square/maskable icon family.
- Athlete pages do not currently declare a favicon or Apple touch icon. Coach pages use the portrait logo as a favicon.
- Static URLs are mostly unversioned. A few public/legacy styles use hand-written query versions.
- There is no version/build identifier presented to the browser and no install or update prompt UX.

Required asset work:

- Produce source artwork with a safe central mark and intentional background.
- Export at least 192×192 and 512×512 `any` icons, 192×192 and 512×512 `maskable` icons, and a 180×180 Apple touch icon. Include tested favicons. Avoid merely padding/cropping the portrait logo.
- Let iOS generate launch screens from supported manifest/icon metadata where possible; if Capacitor later needs native splash assets, generate those from the same source through the native asset pipeline.
- Add manifest fields: stable `id`, athlete-scoped `name`/`short_name`, same-origin `start_url` (prefer `/athlete/dashboard?source=pwa`), `scope`, `display: standalone`, background/theme colors, icon purposes, and conservative orientation behavior.

Do not place a personal athlete/session identifier in `start_url` or the manifest. A current-session shortcut should be resolved after authenticated dashboard load, or be a normal owned route supplied by the server.

### CSP and browser security policy

The private and public apps set a strict policy centrally in `portal/security.py`: same-origin defaults/connect/fonts/forms/media, no framing or objects, no inline scripts/styles, and HTTPS upgrade. Scripts additionally allow `https://cdn.jsdelivr.net`. HSTS, nosniff, DENY framing, strict-origin referrer policy, and a restrictive Permissions Policy are applied.

PWA changes should preserve this posture:

- A same-origin manifest, worker, icons, and JSON API fit the current policy. Explicit `manifest-src 'self'` and `worker-src 'self'` are recommended for clarity.
- Keep worker code external; do not add `unsafe-inline` or `unsafe-eval`.
- Remove the unused CDN script allowance if usage review confirms it is unnecessary.
- `Permissions-Policy` currently denies camera and microphone. That is correct for V7.6 and must not be loosened for hypothetical video. Future native capture permissions need a separate privacy review and least-privilege native configuration.
- Account token pages already use `Referrer-Policy: no-referrer`; preserve that special handling.

### HTTP caching today

The private app calls `init_security_headers(..., prevent_caching=True)`, which sets `Cache-Control: no-store` on **every** response, including authenticated HTML, JSON, redirects, errors, health, manifest if added naïvely, and `/static/*`. Ingress resources add transport/security headers but no cache override. The public lead app does not set a cache directive.

This is secure but prevents useful browser/CDN caching of immutable public assets. Introduce route-aware policy before the service worker:

| Response class | Proposed HTTP policy | Service-worker policy |
|---|---|---|
| Hashed CSS/JS/fonts and non-sensitive icons | `public, max-age=31536000, immutable` | Precache exact revisioned URLs |
| Manifest and worker script | `no-cache` (revalidate; worker may use stricter browser-required handling) | Never cache the worker through its own runtime handler |
| Public marketing content | short explicit TTL + validators, where acceptable | Optional stale-while-revalidate, separate scope if practical |
| Login/logout/account-token responses | `no-store` | Network only; never store responses |
| All authenticated HTML and athlete/coach JSON | `private, no-store` | Network only by default |
| Mutating requests and responses | `no-store` | Network only; never background-replay by default |
| Errors, redirects, `401`, `403`, `404`, `429` | `no-store` | Never cache as route fallback |

Use content hashes or a build revision in static URLs before long-lived caching. A query string changed manually is not a robust deployment/version contract.

## Data that must never be cached

“Never cached” means no shared proxy/CDN cache, Cache Storage response cache, generic runtime cache, precache, or unencrypted browser persistence. It also means no screenshots/telemetry payloads containing the data. Normal browser form memory and the secure session cookie are not a license to persist domain data.

Never cache:

- login HTML after credentials/errors, logout responses, password/invitation/reset pages, account tokens, CSRF tokens, cookies, authentication headers, or rate-limit responses;
- athlete profile and account information, email, federation, weight class, competition data, bodyweight, goals, injury/readiness information, and any identifiers tied to a person;
- programmes, prescriptions, loads, RPE targets, warm-ups, coach notes, current-session state, completed sets, athlete notes, training history, schedule changes, and completion status;
- check-in answers/history, recovery/sleep/adherence scores, free text, coach reviews, and coaching recommendations;
- nutrition records, calories/macros, imports, uploaded CSV/ZIP content, parsed previews, filenames/checksums, bodyweight trends, and coach feedback;
- coach dashboards, athlete lists, applications, meet-day information, operational/security/GitOps/observability data, or any authenticated API response;
- video bytes, thumbnails, signed upload/download URLs, object keys containing personal data, transcoding status responses, or local native file paths.

Safe cache candidates are limited to non-personal, build-versioned application-shell assets: CSS, JavaScript, fonts, generic icons, a generic offline page, and non-sensitive brand artwork. Even these should be separated from authenticated response caching and purged/rotated by build version.

### A narrowly scoped offline-friendly session shell

The safest V7.6 PWA can install and open offline to a generic page saying connectivity is required. It should not display previously fetched athlete HTML.

If product research later proves in-gym offline logging is required, treat it as a separate security/data feature:

1. Cache only the generic shell assets.
2. Store the minimum current-session snapshot and unsent set draft in a dedicated, versioned IndexedDB database—not Cache Storage and not `localStorage`.
3. Opt in explicitly per current session, show “stored on this device”, and provide “remove offline data”. Clear on logout, account switch, session expiry/401, completion, and a short TTL.
4. Prefer platform-protected storage in Capacitor; browser IndexedDB is not encrypted at the application layer. Document device-lock and shared-device risk.
5. Never background-sync “finish session”. Reconnect, re-authenticate, fetch current server version, show conflicts, and require an explicit submit.
6. Give session payloads a server revision/ETag and mutations an idempotency key. Reject or reconcile stale revisions; never last-write-wins silently.
7. Do not cache coach feedback, health/check-in/nutrition data, historical sessions, or other athletes.

## API seams for a future Capacitor shell

Continue using Flask services and authorization; add a thin, versioned athlete boundary rather than duplicating business logic. API identity must always derive the athlete from the authenticated principal—never trust a client-supplied athlete ID.

Small useful seams:

- `GET /api/v1/athlete/me` — identity, role, session expiry, capability flags; no broad profile dump.
- `GET /api/v1/athlete/today` — dashboard summary and owned current-session link.
- `GET /api/v1/athlete/programme` — active programme/week/session summaries with revision metadata.
- `GET /api/v1/athlete/sessions/<id>` — owned prescription and existing log with revision/ETag.
- `PUT /api/v1/athlete/sessions/<id>/draft` — idempotent partial progress save, explicit revision and validation.
- `POST /api/v1/athlete/sessions/<id>/complete` — explicit online completion with idempotency key; no service-worker replay.
- Later, only as demanded: own-user check-in and nutrition read/create endpoints.

Use consistent JSON errors (`code`, safe message, field errors, request ID), `401` for re-authentication, `403/404` without cross-athlete disclosure, CSRF for cookie-authenticated mutations, and `Cache-Control: private, no-store`. Add contract and authorization tests before a native client depends on them.

Server rendering should remain the primary implementation for login/account recovery, dashboard/programme navigation, check-ins, nutrition entry/import, and coach workflows through the PWA phase. Capacitor can initially load those responsive same-origin pages. Extract APIs in order of demonstrated native/offline need, starting with current-session read/save—not as a wholesale SPA rewrite.

## Future video upload architecture (design only)

Video is not part of this implementation. The eventual boundary must be:

1. Authenticated client asks the backend to create an upload intent containing purpose, media type, declared size, and session/set association.
2. Backend authorizes ownership, applies quota/type/size policy, creates an opaque media record, and returns a very short-lived, write-only object-storage upload grant scoped to one randomized object key.
3. Browser or Capacitor client uploads bytes **directly to private object storage** using resumable/multipart upload where supported. Video bytes never pass through Flask/Gunicorn and never land on the AKS/app filesystem or a pod volume.
4. Client tells the backend the upload is complete. Backend verifies object metadata server-side and changes state; asynchronous scanning/transcoding can later consume storage events into isolated derived-object locations.
5. Playback uses short-lived authorized read URLs or a controlled delivery tier. Object containers remain private. Logs and analytics must not retain signed query strings.

The authorization response and signed URLs are `no-store`. Restrict CORS to exact origins/methods/headers, cap expiry and object size, make object names unguessable, record audit events, clean abandoned uploads, and define retention/deletion. The backend authorizes and records; it does not proxy video bytes.

## Staged delivery path

### Stage 1 — responsive web baseline

- Test the athlete money path on representative iOS Safari and Android Chrome devices, including keyboard, 200% text, portrait/landscape, slow network, expiry, logout, and deep links.
- Add safe-area styling and loading/error affordances. Keep form POST semantics.
- Split response caching by sensitivity and introduce content-revisioned static URLs.
- Establish performance budgets; optimize the 651 KB logo and avoid layout shift.

Exit: core flows are usable at 320–430 px and real target devices, no horizontal overflow or obscured actions, authenticated pages remain `no-store`, and deep links return safely after login.

### Stage 2 — installable PWA

- Add the manifest, icon family, touch icon, same-origin worker, and install/standalone smoke tests.
- Precache only revisioned generic shell assets. Use network-only handling for private routes/API and mutations; provide a generic offline page.
- Add a visible, non-disruptive update flow: detect waiting worker, notify the athlete, activate only after consent/safe navigation, then reload. Never switch worker versions mid-submit.
- Expose a non-sensitive build version for diagnostics and delete old named caches on activation.

Exit: installability passes on supported browsers; offline launch shows only the generic shell; private responses never appear in Cache Storage; an update is deterministic and recoverable.

### Stage 3 — Capacitor shell

- Wrap the proven responsive origin with environment allowlisting and navigation interception; do not bundle a forked business UI without a release strategy.
- Prove cookie/CSRF persistence, expiry, account switching/logout data clearance, external-link handling, universal/app links, keyboard/safe areas, back navigation, and iOS/Android network policy.
- Add only the current-session API seams needed by the shell. Define secure local-data rules before any offline athlete record is stored.
- Add crash/diagnostic telemetry with PII redaction and release/build correlation.

Exit: native shells pass the same athlete money path and security tests on iOS and Android, with no broad navigation or credential leakage and a documented web/native version compatibility window.

### Stage 4 — app-store beta

- Prepare signing, bundle IDs, privacy disclosures, support/privacy URLs, screenshots, accessibility checks, account deletion/support process, release notes, and rollback/kill-switch procedures.
- Distribute only to a closed beta cohort after threat modelling and data-protection review.
- Validate review-account handling without weakening production authentication.

Exit: beta evidence and operational ownership are approved. Store submission/release remains a separate authorized activity.

## Acceptance criteria

### Responsive/mobile

- Athlete dashboard, programme, current session, check-in, nutrition entry, login, and logout work at 320, 390, and 430 px with no horizontal page overflow.
- Fixed/sticky controls remain visible above iOS/Android safe areas and virtual keyboards; targets are at least 44×44 CSS px.
- Text remains usable at 200% zoom/dynamic type and reduced-motion settings are respected.
- Tested real-device matrix covers current iOS Safari and Android Chrome plus installed standalone mode.

### Installability and assets

- Manifest is same-origin, valid, linked from athlete/login pages, has stable ID/start/scope/display/colors, and supplies tested `any` and `maskable` 192/512 icons plus Apple touch icon.
- Installation opens the authenticated athlete start route; an owned session deep link survives login and an unknown/foreign session yields a safe 404.
- Lighthouse/browser installability checks and Playwright manifest/standalone smoke tests pass without relying on a CDN.

### Cache and offline safety

- Automated tests assert `no-store` for every private HTML/JSON/auth/token/mutation response and for errors/redirects that could expose state.
- A test enumerates Cache Storage after representative navigation and finds only allowlisted revisioned generic assets.
- Offline launch never exposes an earlier athlete's content. Logout/account switch/401 clears any permitted local private draft.
- POST/PUT/PATCH/DELETE are never served from cache or automatically replayed. Session completion is online and explicit.

### Session, deep links, and updates

- Cookie flags, CSRF enforcement, eight-hour expiry, safe `next`, and role/ownership checks retain automated coverage.
- Installed PWA and Capacitor tests cover cold start, OS restart, expiry, logout, account switch, and revoked/deactivated user.
- Each release has a visible build identifier; old static caches are removed; a waiting update never interrupts an unsaved form or submission.

### Capacitor/API readiness

- Athlete API derives identity server-side, returns consistent errors and revisions, and passes cross-athlete authorization tests.
- Draft mutations are idempotent and conflict-aware; completion cannot be duplicated by retries.
- Supported web/native API compatibility and rollback behavior are documented before beta.

### Future video invariant

- Architecture test/review confirms the backend only creates scoped upload intents and records metadata; clients send bytes directly to private object storage.
- No video request body is accepted by Flask and no video is written to container/pod filesystem. Signed URLs are short-lived, scoped, redacted from logs, and `no-store`.

## Recommended V7.6 boundary

Ship responsive improvements and the installable shell first. Cache only generic, revisioned static assets; keep all athlete data online and `no-store`. Preserve the existing secure SSR login and form flows. Add current-session APIs only when a Capacitor/offline prototype demonstrates the need. Treat offline private data and video as independent security designs with explicit approval gates.
