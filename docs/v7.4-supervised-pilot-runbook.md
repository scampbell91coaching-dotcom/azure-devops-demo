# V7.4 supervised real-athlete pilot runbook

**Scope:** one named athlete, one coach, supervised operation only.

**Go/no-go rule:** do not activate the athlete until every pre-flight item below has an owner and evidence. Stop the pilot if the athlete cannot traverse the production edge and application login, cannot identify the intended session and warm-up, or the coach cannot retrieve a completed log the same day.

This is an operating containment for the V7.3 readiness gaps. It is not approval for unattended onboarding or a multi-athlete launch.

## Owners and pilot record

Record these outside the repository before starting:

- athlete name and confirmed email;
- accountable coach and technical support contact;
- pilot start/end dates and planned session dates;
- agreed completion/urgent-contact channel;
- production release identifier and journey-check timestamp;
- incident log location and stop/rollback decision owner.

Never place passwords, invitation URLs, OAuth tokens, health details, or other athlete data in screenshots, tickets, logs, or this document.

## 1. Account creation and access

- [ ] In a private browser, prove the exact athlete identity can pass the production Entra/OAuth2 edge and reach the Traditional Strength login page.
- [ ] Coach creates the athlete record and checks the email character-for-character with the athlete.
- [ ] Coach generates one invitation and records its delivery state (`sent`, `not configured`, or `failed`) without recording the token.
- [ ] If email is unavailable, coach copies the displayed manual link and sends it through the pre-agreed private channel. Confirm the host is the canonical production HTTPS host.
- [ ] Athlete opens the link in the same supervised window, creates a unique 12+ character password, reaches their own dashboard, signs out, and signs in again.
- [ ] Confirm the invitation cannot be reused. Revoke and regenerate it after failed delivery, accidental disclosure, or use by the wrong browser/person.
- [ ] Confirm the athlete cannot open a known different-athlete session URL or any coach page. Expected results are 404 for cross-athlete resources and 403 for coach-only surfaces.
- [ ] Record pass/fail and timestamp without retaining the invitation URL or password.

**Stop condition:** any uncertainty about edge eligibility, link hostname/recipient, account-to-athlete association, or authorization isolation.

## 2. Session visibility and warm-up contract

- [ ] Coach publishes only the reviewed block. Before publishing, notes state the block start, dated week/session map, planned training days, missed-session rule, and travel/holiday exceptions.
- [ ] Every pilot session contains a coach-authored warm-up in visible session notes: general preparation, lift-specific preparation, ramp sets, and the external pain/urgent-contact instruction.
- [ ] On the athlete account, coach and athlete independently name the dashboard's “Next session” and reconcile it with the dated plan. The product chooses the first unfinished session, not a calendar date.
- [ ] Open the session and verify the warm-up is visible and clearly separate from logged work sets.
- [ ] Verify sets, reps, target load/RPE, exercise notes, and order against the coach's approved prescription.
- [ ] Capture a redacted pass/fail record; do not screenshot athlete data unless the athlete has consented and storage is approved.

**Stop condition:** dashboard order disagrees with the dated plan, warm-up is missing/ambiguous, or published work differs from the approved prescription.

## 3. Mobile acceptance

- [ ] Use the athlete's actual supported phone/browser on the intended mobile network, not only desktop emulation.
- [ ] Check login, dashboard, session notes, warm-up, every set row, numeric keyboard/input, set-note expansion, save/finish controls, and sign-out.
- [ ] Confirm there is no horizontal page overflow and controls are not obscured by the keyboard or sticky footer.
- [ ] Test one non-critical partial save, reload, and resume while the coach is available.
- [ ] Explain that offline operation is not guaranteed. If connectivity is unstable, stop input and contact the coach rather than repeatedly submitting.

## 4. Logging and completion

- [ ] Athlete records completed/skipped state plus actual load, reps, and RPE for each work set.
- [ ] Athlete adds one benign test note and selects **Save progress**. Reload and confirm all saved values belong to the same athlete/session.
- [ ] Athlete reviews entries, selects **Finish session**, accepts confirmation once, and sees “Session complete”.
- [ ] Reload the completed session. Confirm values and note persist, input controls are absent, and the prescription/result history is locked.
- [ ] For mistakes, athlete contacts the coach. Do not edit the database ad hoc; there is no supported completed-log correction workflow.
- [ ] Athlete sends the agreed external “session complete” signal. Pain/injury or urgent matters use the external urgent channel; the platform is not monitored as a safety service.

## 5. Coach review

- [ ] On the same day, coach checks the external completion signal.
- [ ] Coach opens the athlete record and the **Completed sessions** section, then selects **Review training**.
- [ ] Match athlete, session, timestamp, prescription snapshot, results, and notes to the athlete's submission.
- [ ] Confirm no other athlete's data appears in the reviewed page.
- [ ] Record review completion in the external pilot log and send feedback through the agreed channel.
- [ ] Repeat this manual poll daily while the pilot is active.

**Known P0 containment:** completed training does not enter **Athletes requiring review**. That queue covers submitted weekly and unreviewed nutrition check-ins only. Never treat a clear queue as proof that training has been reviewed.

## 6. Operational health

Before invitation and before each pilot session:

- [ ] Confirm the deployed release identifier and expected configuration.
- [ ] Confirm ingress/OAuth and the application login page respond from outside the coach's existing session.
- [ ] Confirm `/health` succeeds and perform an authenticated read plus disposable/non-critical write-and-reload journey; `/health` alone does not prove database writes.
- [ ] Check application/Gunicorn and platform logs for recent 5xx, database, login, invitation, or CSRF failures. Do not paste sensitive request content into the incident log.
- [ ] Confirm the database backup/PITR declaration and who can perform restore-to-new-server. Record that restore remains manual and must not be improvised during the session.
- [ ] Confirm coach and technical support availability for the full athlete session plus review window.
- [ ] Record checks, times, release, result, and owner in the pilot log.

## 7. Support, incident stop, and rollback

Stop new athlete activity immediately for cross-user data exposure, wrong-account activation, repeated/ambiguous submissions, unavailable prescriptions/warm-ups, corrupted or missing saved results, sustained authentication failure, or unexplained 5xx/database errors.

1. Tell the athlete to stop submitting and preserve the current screen without sharing secrets.
2. Record UTC/local time, release, route, action, visible error, affected synthetic/athlete identifier per privacy policy, and request correlation if available. Do not record credentials or invitation URLs.
3. Revoke any exposed invitation/reset token and deactivate access through the supported operational process if account integrity is uncertain.
4. Preserve application/platform logs and database state. Do not delete or directly rewrite athlete logs.
5. Technical owner chooses: retry only after a known transient fault, roll the deployment back through the documented GitOps release process, or restore the database to a new server through the documented recovery process.
6. A deployment rollback does not reverse database writes. Verify schema compatibility and current data before rollback; no migration is introduced by this pilot path.
7. After recovery, repeat edge login, athlete authorization isolation, session read, non-critical write/reload, and coach retrieval before resuming.
8. Inform the athlete what is known, the safe next action, and when support will update them. Use the external channel.

## Exit criteria

At the end of the pilot, retain a redacted record of account activation, session/warm-up visibility, mobile acceptance, partial-save persistence, completion persistence, same-day coach review, operational checks, incidents, and support effort. Review the observed friction before adding athletes. Unattended onboarding remains no-go until production edge/invitation delivery is proven and completed training has a reliable reviewed/unreviewed queue workflow.
