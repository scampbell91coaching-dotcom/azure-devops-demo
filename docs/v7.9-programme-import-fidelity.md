# V7.9 programme import fidelity audit

## Verdict

**No source-to-programme import exists, so fidelity to an external programme corpus is not currently demonstrable.** The repository contains no programme CSV/XLSX parser, programme import service, programme import route, or source-programme fixture. The imports that do exist are for MyFitnessPal nutrition data and exercise-library knowledge. A coach cannot import a rich programme and receive either a faithful result or a loss report.

The closest auditable ingestion boundary is Block Factory: a structured, integrity-protected proposal is accepted and converted into `TrainingBlock` / `TrainingWeek` / `TrainingSession` / `ExercisePrescription` rows. That conversion preserves basic hierarchy, exercise order, accessory count/order, sets/reps and generated RPE, but materially flattens coaching intent. It is not a safe surrogate for programme import.

One independent fidelity defect was fixed during this audit: duplicating a session, week, or block discarded authored warm-up assignments and overrides. Copy workflows now preserve those inputs while correctly excluding resolved athlete snapshots (execution history).

## Scope and method

Repository-wide searches covered programme/program import terminology, CSV/XLSX/ODS assets, upload routes, import services, fixtures, models, migrations, template application, Block Factory proposal acceptance, duplication services, warm-up persistence, and relevant tests. No external/source programme corpus was present, so this audit does not invent expected values or claim representative-corpus coverage.

The evidence-backed comparison is:

1. Block Factory request and proposal payload as the source representation.
2. Factory-generated ORM rows as the destination representation.
3. Authored programme duplication as an intra-repository fidelity boundary.
4. The destination schema as a capacity check for fields requested by V7.9.

## Concrete mismatches

### P0 — there is no programme importer or fidelity contract

There is no accepted input format, parser, validation report, rejected-field report, provenance record, source identifier/hash, or golden source-versus-destination fixture. Consequently an imported programme cannot be distinguished from hand-authored/generated data, replayed idempotently, or audited for omissions.

This is a release blocker if V7.9 claims programme import. A valid implementation needs a versioned canonical input contract and a lossless-or-explicitly-rejected rule for every field below before production code is written.

### P1 — Factory source metadata is discarded on acceptance

The request captures goal, split, week count, training days, lift frequencies, deadlift style, meet date, accessory selection/mode/volume, deadlift grip, grip priority and strap usage (`platform-portal/portal/block_factory.py:195-254`). `_proposal_payload` serialises the request, so these values are part of the accepted source proposal (`platform-portal/portal/block_factory.py:743-750`). Acceptance creates a block with only athlete and name, generic week/session labels, and prescriptions (`platform-portal/portal/block_factory.py:952-1044`).

Concrete losses after acceptance include:

- meet date and competition phase/intent;
- goal/split and requested lift-frequency rationale;
- deadlift style as explicit metadata (only the resulting exercise name survives);
- grip, strap usage and grip-work priority;
- accessory mode and volume policy;
- proposal version/source linkage and integrity hash.

The destination block has only name, objective, status and timestamps; week has name/position/notes; session has name/day label/position/notes (`platform-portal/portal/models/programming.py:23-113`). There is nowhere structured to retain most of the accepted source values.

### P1 — accessory selection explanations are flattened

Factory preview preserves accessory order and records each accessory's role, source, provenance, and (for automatic suggestions) reasons (`platform-portal/portal/block_factory.py:591-660`). Acceptance persists name, position and provenance, but does not persist role, source, or reasons (`platform-portal/portal/block_factory.py:998-1041`). Thus the exercise survives while the coaching justification for choosing it does not.

Manual accessory count and order are preserved: selected IDs are converted in submitted order and distributed deterministically across days (`platform-portal/portal/block_factory.py:552-568`, `591-611`); destination `position` follows the final exercise list. Automatic count is intentionally reduced to one, two or three suggestions per day according to the selected volume (`platform-portal/portal/block_factory.py:570-574`, `632-660`).

### P1 — generated prescriptions discard available prescription detail

`ExercisePrescription` can represent sets/reps, rep ranges, fixed and capped load, percentage, RPE/range/cap, target single data, AMRAP, tempo, rest and free-text notes (`platform-portal/portal/models/programming.py:298-339`). Factory acceptance populates only sets, reps, prescription type and RPE (`platform-portal/portal/block_factory.py:1027-1041`). Even when an accessory catalogue row has default RPE or default rest, generation only consumes default sets and reps (`platform-portal/portal/block_factory.py:1022-1025`).

This means tempo, rest periods, RPE caps, load prescriptions and coaching notes cannot survive that source-to-row conversion because they are not in the Factory source contract and are not populated at acceptance.

### P1 — no structured pairing/superset representation

Exercise order is represented by one integer `position`, but neither `TrainingSession` nor `ExercisePrescription` has a pairing/group/circuit field (`platform-portal/portal/models/programming.py:86-113`, `298-339`). Encoding `A1/A2`, supersets, alternating rest, or circuit rounds in notes would be ambiguous flattening rather than preservation.

### P1 — substitutions, constraints and variant intent are not snapshotted

The exercise catalogue contains variation, equipment, coaching cues, equipment options, constraint tags, variation lineage and swap groups. A prescription stores an optional exercise foreign key plus a name and notes. Therefore:

- a named variant can survive as the exercise name/link;
- equipment constraints, allowed substitutions, grip/setup requirements and competition relevance are not programme-level snapshots;
- later catalogue edits can change the meaning displayed for an old programme;
- a free-text prescription note is the only current place for source-specific grip/strap/setup instructions.

That is insufficient for an importer promising faithful, reviewable intent.

### Fixed — duplication omitted warm-ups/preparation drills

Warm-up assignments and overrides are keyed independently by `session_id` (`platform-portal/portal/models/warmup.py:49-86`). Existing duplication copied session metadata, lift slots and prescriptions only. `portal/programming_services/warmups.py` now copies assignment provenance/reason and every authored override field for session, week-extension/duplication, and block duplication. It deliberately does not copy `WarmupPlanSnapshot`, which is a resolved athlete/session historical record (`platform-portal/portal/models/warmup.py:89-119`).

The focused regression creates a protocol assignment, an appended preparation drill with sets/reps/rest/cue/reason, and a resolved snapshot. It proves authored intent appears on the copied session and the historical snapshot does not (`platform-portal/tests/test_session_lifecycle.py`).

## What is already safe

- Hierarchical ordering is explicit: block weeks, week sessions and session prescriptions are ordered by position.
- The duplication path uses `ExercisePrescription.copy_values()`, covering all supported prescription data fields, and existing lifecycle tests compare copied values.
- Lift slots and their top-set/back-off role links are remapped to the new session rather than pointing back to the source.
- Completed-set rows snapshot prescribed reps/load/RPE, so subsequent programme edits do not rewrite those limited execution-history values.

These strengths do not establish external import fidelity; they only reduce loss once data is already represented by the current schema.

## Required acceptance gate for a future importer

Before enabling an import route:

1. Commit a redacted, coach-approved corpus covering at least one off-season block, one meet-prep block, pairings, warm-ups, variants, equipment constraints, substitutions, load and RPE-cap modes.
2. Define a versioned canonical fixture with stable source IDs and explicit ordering at block/week/session/exercise/warm-up/pairing levels.
3. Make preview report every source field as `preserved`, `normalised`, or `rejected`; never silently drop a field.
4. Persist source format/version/hash and an import ID on the resulting programme.
5. Compare canonical source and exported destination semantically in golden tests, including accessory cardinality/order and all coaching text.
6. Reject unsupported pairings, constraint semantics or prescriptions until the schema can represent them; do not concatenate them into generic notes without coach approval.
7. Prove idempotent replay and rollback on any invalid row.
