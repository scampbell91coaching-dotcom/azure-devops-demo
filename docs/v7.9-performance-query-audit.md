# V7.9 performance and query audit

Date: 2026-08-10

## Scope and method

This audit traced the Flask/SQLAlchemy request paths for the coach dashboard, coach athlete detail, athlete dashboard, programming hierarchy, Block Factory, nutrition history, client-service entitlements, persisted warmups, and the current macro/meal-plan seams. SQL `SELECT` statements were measured with SQLAlchemy's `before_cursor_execute` event in representative tests. Scaling assertions compare small and larger aggregates so relationship-loading regressions cannot hide behind a changed fixed overhead.

No caching, pagination, or policy changes were introduced. The changes in this audit only alter how existing rows are loaded.

## Results

| Surface | Finding | Outcome / risk |
| --- | --- | --- |
| Coach dashboard | Uses six aggregate reads plus one batched nutrition-entitlement read. Training log results use `selectinload`; query count remains **7 SELECTs for 12 athletes**. | No N+1 found. However, weekly check-ins, nutrition check-ins, completed logs, and blocks are loaded without date/status bounds. Runtime and memory grow with all-time history. |
| Coach athlete detail | Loads all `NutritionCheckIn` rows and sorts them in Python. It separately loads imported nutrition, training logs, account tokens, and service history. | No row-by-row query loop after entitlement fix, but history and response payload are unbounded. Pagination or a product-approved history window is needed before large histories accumulate. |
| Athlete dashboard | Current block weeks/sessions are batched; check-ins and trends have explicit limits (4, 6, or 12). Entitlement is resolved once. | Bounded and no collection N+1 found. Several separate nutrition queries overlap, so a later repository-level projection could reduce fixed reads without changing the bounded behavior. |
| Block page | Previously lazy-loaded sessions once per week and lift slots once per session. | Fixed with nested `selectinload`. The query-count test renders 1-week/3-session and 8-week/24-session blocks with the **same SELECT count**. HTML still grows linearly with weeks, so very long blocks need pagination/collapsing as a product decision. |
| Week page | Previously lazy-loaded prescriptions and lift slots per session, then prescriptions per lift slot. | Fixed with batched relationship loading. Exercise catalogue choices remain one query. HTML repeats the full exercise selector for every slot, which is a payload/DOM risk as both sessions and catalogue size grow. |
| Session page | Previously lazy-loaded hierarchy, prescriptions, lift slots, and slot prescriptions. | Fixed with joined hierarchy and batched collections. Warmup inputs remain separate fixed queries. |
| Athlete programme page | Schedule projection traversed active block weeks/sessions lazily. | Fixed by batching weeks and sessions for all loaded blocks. Query growth no longer follows week count. Loading every archived block plus its hierarchy may become excessive; only the active block needs its full hierarchy for schedule projection. |
| Block Factory | Athlete list and accessory catalogue are each loaded once; preview taxonomy lookup is batched by exercise name. | No N+1 found. Every GET/preview sends the entire accessory catalogue and preview repeats the catalogue queries. Search/autocomplete with a compact JSON endpoint is the future mitigation if catalogue/payload size becomes material. |
| Nutrition dashboard/history | Coach nutrition dashboard loads all dedicated and nutrition-enabled weekly records, then sorts/groups in Python. Athlete dashboard histories are bounded, but coach athlete detail is not. | No N+1; high history-volume risk. A database window-function/latest-N projection is recommended, retaining explicit “view older” pagination. |
| Service entitlements | `resolved_client_services` loaded the same athlete history twice and lazily fetched up to one `User` per service provenance. The coach dashboard already uses a batch resolver across athletes. | Fixed: one joined history query now resolves the profile, scheduled decisions, and coach provenance. Test measurement is **1 SELECT for four services set by four coaches**. |
| Warmup resolution | Each assignment lazily loaded its protocol and steps, producing approximately `2N + 2` reads. Snapshot steps were also lazy on athlete delivery. | Live resolution fixed with `selectinload`: **4 SELECTs for one or five assigned protocols** (assignments, protocols, steps, overrides). Snapshot delivery remains a fixed two-read path; eager loading could reduce it to one joined read but is not an N+1. |
| Macro/meal-plan seam | Current macro prescription and meal-plan services are domain/in-memory repositories; no ORM page seam exists yet. Macro totals are recomputed through nested properties and full meal/day structures are returned. | No query issue today. Before persistence, require batch food lookup, bounded effective-date queries, summary projections for history lists, and pagination/lazy detail for long plans. Avoid one food query per meal item and one prescription query per rendered day. |

## Changes made

- Added nested eager loading to block, week, session, and athlete-programme GET routes.
- Batched warmup assignment → protocol → step resolution.
- Reused the already-loaded entitlement history and eager-loaded provenance users.
- Added query-count regression tests for long programmes, entitlement provenance, and multiple warmup protocols.

These changes preserve ordering, filtering, defaults, legacy entitlement compatibility, warmup override application, and rendered content.

## Follow-up priorities

1. Add product-approved pagination to coach athlete nutrition history and completed training logs.
2. Replace coach dashboard all-history reads with bounded “needs review”, latest-per-athlete, and recent-window database queries.
3. Project latest/four recent nutrition records per athlete in SQL instead of loading the complete nutrition estate.
4. Keep the programming query-count tests and add response-size budgets once supported limits for blocks, sessions, catalogues, and meal plans are defined.
5. When meal plans become persistent, design list/detail projections and batch food/macro hydration before wiring them into page templates.
