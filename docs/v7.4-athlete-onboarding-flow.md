# V7.4 athlete onboarding and invitation pilot

## Readiness decision

The application invitation lifecycle is suitable for a supervised pilot. General athlete onboarding is **not yet proven** because production places Microsoft Entra/OAuth2 Proxy in front of every application route, including invitation activation. The exact pilot athlete must be able to pass that edge before an invitation is sent.

The two boundaries have different jobs:

1. OAuth2 Proxy authenticates an identity accepted by the configured Microsoft tenant before nginx forwards any private-platform request.
2. Flask authenticates and authorizes the Traditional Strength user, applies coach/athlete roles, binds an athlete user to one athlete record, and owns session expiry.

That is an expected defence-in-depth design for an internal coach portal. It is also a product defect for external athlete onboarding until athlete eligibility at the edge is intentional, documented, and tested. V7.4 does not bypass either check. After the edge succeeds, Flask uses `X-Auth-Request-Email` only to prefill the email field and still requires the application password.

## Exact first-time journey

1. The coach creates the athlete with the final, confirmed email address.
2. The coach submits **Invite athlete** and retypes that address. Flask creates or reuses an inactive athlete `User`, revokes older unused invitations, stores only a SHA-256 token digest, and creates a 48-hour invitation.
3. Flask builds an HTTPS activation URL from `ACCOUNT_PUBLIC_BASE_URL` when configured, otherwise from the request host. The token is in the URL fragment so browsers do not send it to nginx, OAuth2 Proxy, Flask, access logs, or referrers.
4. SMTP either accepts the message or the coach sees a one-display manual link. “Accepted” is not proof of inbox delivery; the athlete must confirm receipt.
5. The athlete opens the link. Production first redirects an unauthenticated browser through `/oauth2/start` and Microsoft Entra, then returns to the original invitation path. The URL fragment remains client-side.
6. JavaScript moves the token from the fragment into the activation form and removes it from the address bar. The athlete chooses a password of at least 12 characters.
7. Flask atomically checks purpose, digest, expiry, revocation and consumption; activates the linked user; marks the token consumed; creates the Flask session; and redirects to `/athlete/dashboard?welcome=activated`.
8. The first authenticated page explicitly confirms **Account activated**. Athlete authorization permits athlete endpoints only and hides other athletes.
9. On a later visit, OAuth2 Proxy may reuse its edge cookie. If the Flask session has expired, `/login` is shown with the edge email prefilled; the Flask password remains mandatory.

Expired, revoked, malformed and replayed links return an unusable-link response. Issuing another invitation revokes the previous unused invitation. No schema change is required.

## Delivery verification without secrets

Run the redacted configuration check in the same runtime/configuration as the private portal:

```bash
flask --app app account-delivery-readiness
```

It reports only the public base URL, whether a transport exists, whether TLS is enabled, and whether SMTP authentication is configured. It never prints the SMTP host, username, password, invitation token, recipient, or message body.

Interpretation:

- `public_base_url` must be `https://platform.traditionalstrength.co.uk` for the production pilot.
- `transport: configured` means the application can attempt SMTP; it does not prove inbox delivery.
- The account-delivery page records `sent`, `not configured`, or `failed`. `sent` means SMTP accepted the message.
- Delivery is proven only when the intended athlete confirms receipt and opens the one-time link.
- If SMTP is unavailable, use the displayed manual link once, through a pre-agreed end-to-end encrypted or otherwise trusted channel. Never paste it into tickets, logs, screenshots, or shared documents.

## One-athlete pilot runbook

### Before sending

1. Name an operator, the athlete, a support contact, and a 30-minute test window.
2. Confirm the athlete can sign into the production Entra edge in a private browser. Stop if this fails; an application invitation cannot repair edge eligibility.
3. Run `flask --app app account-delivery-readiness` in the deployed app context. Stop if the public base URL is absent or not the production HTTPS host.
4. Confirm the athlete record’s email character-for-character over a separate trusted channel. Ensure the athlete has a password manager available.
5. Open the athlete dashboard and confirm the account is not already active. Revoke any invitation that may have been exposed.

### Send and activate

1. Submit **Invite athlete**, retyping the confirmed email.
2. Record only UTC time, athlete internal ID, operator, and the displayed delivery state. Do not record the token or full URL.
3. For `sent`, ask the athlete to confirm receipt and sender/subject, without forwarding the link. Allow ten minutes and check spam once.
4. For `not configured` or `failed`, copy the one-display manual URL directly into the agreed private channel. Ask the athlete to acknowledge receipt; do not retain another copy.
5. The athlete opens the link in the already edge-authorized private browser, sets a unique 12+ character password, and confirms the first page says **Account activated**.
6. The athlete signs out, closes the browser, returns through the normal production URL, completes edge authentication if requested, and signs in to Flask. Confirm the landing page is the athlete dashboard and the email is prefilled after the edge.
7. Ask the athlete to open Programme and verify only their name/content is visible. A coach separately confirms the account state is active.

### Negative checks and evidence

1. Reopen the original invitation URL after activation. It must report that the link cannot be used.
2. Record statuses and timestamps only: edge passed, delivery state, receipt confirmed, activation passed, replay rejected, second login passed, first landing passed, and operator sign-off.
3. Do not capture cookies, authorization headers, query strings, URL fragments, passwords, SMTP values, or personal training/health content.
4. If the link is disclosed or activation fails before consumption, revoke it from the coach UI and issue a new invitation. If SMTP claims acceptance but no message arrives, use a newly issued manual link and record SMTP delivery as unproven.

## Deterministic automated evidence

`platform-portal/tests/test_account_lifecycle.py` covers digest-only storage, inactive account creation, valid activation, explicit first landing, expiry, replay prevention, revocation/reissue, duplicate ownership, password reset and coach/athlete authorization. `platform-portal/tests/test_auth.py` covers safe login redirects, role landings, the non-authenticating edge-email hint, password enforcement, rate limiting, CSRF and the redacted readiness command. `e2e/tests/auth.spec.ts` drives manual invitation through activation and replay rejection in a browser.

These tests prove repository behaviour in disposable test environments. They do not prove production Entra eligibility, SMTP inbox delivery, DNS, or the deployed redirect chain; the pilot steps above supply that evidence.
