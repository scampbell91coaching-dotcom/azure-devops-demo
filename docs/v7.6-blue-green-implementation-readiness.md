# V7.6 Blue/Green implementation readiness

Status: implementation plan only. This document does not authorize a production, Argo CD, workflow, database, Azure, or DNS change.

## Decision summary

The private portal can move to two fixed slots without changing its public hostname. The stable `platform-portal-private` Service remains the only traffic switch and selects exactly one of `slot: blue` or `slot: green`. The Ingress and OAuth2 Proxy remain stable.

Four changes are required before this is safe:

1. Remove the unused `platform-portal-private-data` RWO PVC from portal pods after a read-only production preflight. PostgreSQL is authoritative; no application code uses `/data`.
2. Put traffic resources in a separate Argo CD Application/path from release resources. A selector-only commit must not reconcile the application containing the PreSync migration/seed hook.
3. Make status and deployment verification explicitly slot-aware.
4. Replace the three overlapping portal ingress policies with one label-based, slot-neutral policy model.

Canary is deliberately absent. The `slot` and stable-Service boundary leave a later weighted-routing extension point without changing slot identity.

## `/data` and the RWO decision

Static tracing found only the Kubernetes mount and stale explanatory/test examples for the private portal:

- `DATABASE_URL` comes from `flask-runtime-secrets`; deployed state is PostgreSQL.
- `platform-portal/portal/database_config.py` mentions `/data` only as a generic SQLite example. It returns the supplied PostgreSQL URI unchanged apart from driver normalization.
- `platform-portal/Dockerfile.private` copies immutable catalogue/intelligence content to `/app/data`, not `/data`.
- status snapshots use the distinct `platform-status-snapshots` Azure Files RWX claim mounted at `/status`.
- the migration Job has no `/data` mount.
- no private-portal Python runtime path reads or writes `/data`.

Therefore `platform-portal-private-data` is neither authoritative nor required. The safest target is **remove the dependency**, not create slot-local copies and not replace it with RWX. Slot-local copies would imply false persistence semantics; RWX would preserve an unexplained writable shared surface.

Before removal in a later authorized change, perform these read-only checks against the live Blue pod: confirm `DATABASE_URL` has an approved PostgreSQL scheme without printing its value; inspect mount and open-file metadata without displaying file contents; list `/data` filenames, sizes, owners, and hashes; and confirm application logs/config do not identify it as a store. If unexpected data or an open writer exists, stop and classify/backup it before proceeding. After the first dual-slot release, retain the unmounted PVC for the agreed rollback window, then delete it in a separate approved change. Rollback before deletion is remounting it on the former single-slot manifest; no cutover depends on it.

## Target resource model

Every portal pod carries `app.kubernetes.io/name: platform-portal-private`, `app.kubernetes.io/component: web`, and `slot: blue|green`. Deployment selectors are immutable and include name, component, and slot.

| Resource | Stable identity and purpose |
|---|---|
| `Deployment/platform-portal-private-blue` | Fixed Blue slot; independently pinned immutable image. |
| `Service/platform-portal-private-blue` | Direct validation Service selecting only Blue. ClusterIP, port 80 to `http`. |
| `Deployment/platform-portal-private-green` | Fixed Green slot; independently pinned immutable image. Initially may match Blue, then receives the candidate. |
| `Service/platform-portal-private-green` | Direct validation Service selecting only Green. ClusterIP, port 80 to `http`. |
| `Service/platform-portal-private` | Stable production switch. Same name/port; selector includes common name/component plus exactly one `slot` value. |
| Ingress and OAuth resources | Unchanged names, hostname, TLS secret, callback and stable Service backend. |

Direct slot Services are cluster-internal only. Validation uses their DNS names and does not add a public Green Ingress or bypass OAuth at the edge.

## Migration and seed boundary

Split reconciliation into two paths and Applications:

- `private-platform-manifests/release/`: both slot Deployments/Services, migration Job, collector, status PVC/RBAC/CronJob, OAuth workload/Service, and NetworkPolicies. Existing `platform-portal-private` Application watches this path.
- `private-platform-manifests/traffic/`: stable switching Service and both Ingresses. New `platform-portal-private-traffic` Application watches only this path with the same destination and automated prune/self-heal policy.

The release promotion changes only the inactive slot image and the release Job image in one commit. The release Application's PreSync Job runs the candidate image in this order: `flask db upgrade`, `flask seed-exercise-catalogue`, `flask seed-programming`, `flask verify-production-db`. Only after success can Argo update the inactive Deployment. Seeds remain idempotent, but idempotence is defense in depth rather than the traffic-switch mechanism.

The cutover commit changes only `traffic/stable-service.yaml`. The release Application has no desired-state diff, while the traffic Application contains no hook; therefore a selector-only cutover cannot rerun migrations or seeds. CI must assert both path isolation and absence of hook annotations/Jobs in the rendered traffic path.

Use a deterministic Job name containing a sanitized candidate image digest/SHA rather than `generateName`, for example `platform-portal-private-release-<sha12>`, with `BeforeHookCreation,HookSucceeded`. Promotion code updates the Job name and image together and rejects a non-SHA image. This gives the release an auditable identity and prevents an unrelated edit from silently presenting an old Job as candidate evidence. Database changes must follow expand/migrate/contract: expand before either slot needs the schema, migrate/backfill while both versions can operate, and contract only in a later release after Blue rollback is intentionally retired.

## Promotion, validation, cutover, and rollback contract

1. Determine active slot from the Git stable-Service selector; fail closed unless it is exactly Blue or Green. The other fixed slot is the candidate.
2. Promote the new immutable image to the inactive Deployment and release Job only. Never update the active Deployment.
3. Release Application PreSync completes database expand/migrate/seeds/verification. Failure leaves stable traffic unchanged.
4. Wait for candidate rollout and prove its image exactly matches the candidate.
5. Validate candidate through its direct ClusterIP Service: shallow health, database compatibility, authenticated application smoke tests from an approved in-cluster runner, logs/restarts, and status schema identity. Also prove current stable traffic remains healthy.
6. At the approval gate, commit only the stable Service slot selector. Confirm the Git diff contains one scalar selector change and no image, Job, Ingress, OAuth, or migration change.
7. Wait for the traffic Application to be Synced/Healthy; verify Service endpoints belong only to the new slot, stable internal health succeeds, and the unchanged external hostname still redirects anonymous users to OAuth and passes the authenticated smoke path.
8. Retain the prior slot unchanged and ready for the rollback window.

Application rollback is another reviewed selector-only Git commit to the prior slot, followed by endpoint and external verification. Do not use `kubectl patch`; self-heal would revert it and Git would cease to describe traffic. Database rollback is not an Alembic downgrade during an incident. Because both versions must remain compatible, switch traffic back and forward-fix the database. If a migration makes the old slot incompatible, cutover is forbidden and the release is failed before selector change.

## Implementation order and checkpoints

| Phase | Work | Go checkpoint | Failure action |
|---|---|---|---|
| 0. Baseline | Capture rendered manifests/tests and perform authorized read-only `/data` and DB-scheme checks. | `/data` confirmed non-authoritative; current health/evidence saved. | Stop on any writer or unexplained data. |
| 1. Offline contracts | Add YAML-aware promotion/status logic and unit/render tests first. | All tests below pass without cluster access. | No live effect; revise design. |
| 2. Ownership split | Introduce release/traffic paths and two Applications in a reviewed change plan. | Exactly one owner per object; traffic path has no Job/hook. | Do not sync; fix collisions/prune ordering. |
| 3. Slot resources | Convert current workload to Blue and introduce Green with the same known-good image; remove pod `/data` mount but retain PVC initially. | Both direct Services healthy; stable still selects Blue; external behavior unchanged. | Selector remains/reverts Blue; diagnose Green. |
| 4. Candidate release | Promote only Green plus release Job. | Migration succeeds; Green image/readiness/DB/smoke evidence passes; Blue/stable healthy. | Leave traffic on Blue; fix forward or abandon candidate. |
| 5. Cutover | Approved one-line selector commit Blue to Green. | Traffic app synced; endpoints only Green; internal/external/auth checks pass. | Commit selector back to Blue. |
| 6. Hold | Keep Blue image and replicas unchanged; observe agreed window. | Error/latency/auth/data checks remain acceptable. | Roll back selector to Blue. |
| 7. Cleanup | Later, separately approve contract migrations and PVC deletion. | Blue rollback explicitly retired; backups/retention satisfied. | Defer cleanup; it is never on cutover critical path. |

Prune/rename safety matters in phase 2: first establish the traffic Application without duplicate resource ownership, then change the release Application path. Rehearse the exact Argo diff offline and use sync waves only for ordering inside one Application; waves do not isolate hooks across selector changes.

## Tests required before any live change

Run all tests in CI against rendered YAML and a disposable Kubernetes namespace (kind/k3d is sufficient for routing mechanics; PostgreSQL integration needs a disposable PostgreSQL instance):

- kubeconform strict validation for both paths and both Application manifests.
- policy tests proving exactly two fixed slot Deployments/direct Services, immutable selectors, stable Service selecting one slot, no public slot Ingress, unchanged production hostname/OAuth callback, and no `/data` volume/mount.
- ownership test proving every `(apiVersion, kind, namespace, name)` occurs once across both rendered paths and the traffic path contains no `Job` or Argo hook annotation.
- promotion unit tests listed above and a golden diff asserting candidate promotion cannot edit traffic while cutover can edit only the stable selector.
- collector unit/manifest/UI tests for schema v2 and all invalid/partial states.
- NetworkPolicy render tests proving both slots receive the same ingress policy and no obsolete duplicate policy names remain; in a disposable cluster, allow ingress-nginx/production probes and deny an unrelated namespace.
- migration rehearsal from a production-shaped sanitized backup: old image before/after expand migration, new image after migration, idempotent seeds, lock/duration limits, and explicit proof that switching the Service twice creates no Job.
- endpoint tests: Blue direct, Green direct and stable endpoints; endpoint-slice membership exactly matches selector; zero/ambiguous endpoints fail the gate.
- authenticated browser/API smoke against the candidate path without a new public hostname, plus anonymous external redirect and unchanged TLS/host assertions.
- rollback rehearsal: Blue active, Green candidate, cut to Green, commit back to Blue; verify no image mutation, no migration rerun, and persisted PostgreSQL writes remain visible to both compatible versions.
- existing `pytest -q platform-portal/tests`, private manifest validation, Playwright suite, image scan, credential separation tests, and GitOps concurrency tests.

No production sync should begin until these pass, the `/data` preflight is signed off, the migration is classified expand/migrate rather than contract, and both cutover and rollback commits have named operators and evidence destinations.

## Future canary extension point

Keep consumers keyed to a generic slot identity and make the stable Service selector parser explicit. A future canary design can add weighted ingress/service-mesh routing in a separate proposal while Blue and Green Services remain stable validation targets. Kubernetes Service selectors are binary, so do not overload the V7.6 selector with weights or add a third slot now.
