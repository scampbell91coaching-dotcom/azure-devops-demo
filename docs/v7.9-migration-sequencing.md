# V7.9 database and migration sequencing review

## Decision

V7.9 should ship as two additive Alembic revisions, in a single linear chain:

```text
0015_client_services (current head)
  -> 0016_macro_prescriptions (expand)
  -> 0017_meal_plan_persistence (expand)
  -> later data migration / legacy-read retirement
  -> later contract revision(s)
```

The revision names above are reserved examples, not migrations created by this
review. The macro revision must land first because a meal-plan assignment binds
to an immutable prescription identity and snapshots its targets. Neither V7.9
revision should remove or reinterpret existing nutrition check-in columns.

At review time, `flask --app app db heads` reports exactly
`0015_client_services (head)`. The on-disk graph is linear from `0001` through
that revision. Integration must re-run this check: concurrent feature branches
must rebase their `down_revision` onto the accepted head, or add one reviewed
merge revision before either V7.9 revision. Do not deploy two heads and do not
use `upgrade heads` as a substitute for resolving the graph.

## Compatibility envelope

| Combination | Required behavior |
| --- | --- |
| Old app + old schema | Unchanged. |
| Old app + expanded V7.9 schema | Safe: old code ignores new tables; existing columns, constraints, defaults and meanings do not change. |
| New app + expanded V7.9 schema | Supported after its corresponding PreSync job succeeds. |
| New app + old schema | Unsupported for persistence paths. Keep new reads/writes disabled until schema readiness is verified; importing models alone must not query the new tables. |

The last row matters during rollback and local/test startup. A feature flag is
not a schema migration mechanism, but it provides a deployment gate: default
macro and meal-plan persistence off, run PreSync, verify the Alembic revision
and required constraints/indexes, then enable application paths. Health checks
should remain independent of optional feature tables, while a separate release
readiness check must fail closed if a feature is enabled without its schema.

## Revision 1: macro prescription expand

Persist an immutable prescription header containing a stable public identifier,
`athlete_id`, inclusive `effective_from`/`effective_until`, daily targets,
nullable training/rest overrides, optional fibre, meal count and notes, plus
source, source reference, recorded time and actor snapshot. A normalized target
child table is also viable, but daily/training/rest must have a database-level
unique key and daily must be guaranteed at publication. Pick one representation
before implementation and keep the repository boundary independent of it.

Required integrity:

- foreign key from prescription to athlete; actor user FK should use `SET NULL`
  while retaining immutable actor ID/role/display snapshots;
- unique stable prescription ID;
- checks for valid date ordering, target bounds, valid source/day type, and meal
  count; preserve the domain rule that calories need not equal macro arithmetic;
- a covering lookup index beginning `(athlete_id, effective_from)` and including
  `effective_until` (or an equivalent PostgreSQL range index);
- no overlapping inclusive prescription periods for one athlete.

On PostgreSQL, prefer a GiST exclusion constraint on athlete equality and an
inclusive `daterange`, with open-ended rows mapped to infinity. This normally
requires the reviewed `btree_gist` extension. Make the constraint deferrable if
the application closes the old interval and inserts its successor in one
transaction. If the extension is not approved, use a transaction-scoped
per-athlete advisory lock plus an overlap query, and retain an explicit database
backstop (for example a trigger); an application-only pre-check races.

Prescription content is append-only history. Correction creates a new record
and supersedes the previous one; it never rewrites targets or provenance already
used by a check-in or assignment. If the chosen representation closes an
open-ended row, that single monotonic `effective_until` transition must be the
only permitted header update, be audited, and occur atomically with the
successor insert. A stricter design can append a supersession event and maintain
validated effective periods separately. Adjacent intervals are legal because
the domain's ends are inclusive only when
`old.effective_until < new.effective_from` (usually the previous day).
Resolution must raise on ambiguity rather than choose the latest row.

Do not backfill prescription rows from `NutritionCheckIn` target columns in this
revision. Those fields are athlete-copied historical snapshots with insufficient
provenance and cannot safely become coach prescriptions.

## Revision 2: meal-plan persistence expand

Base this revision only on the accepted macro revision. The minimum relational
shape is:

- templates and immutable template revisions;
- revision-owned ordered days, meals and meal items;
- catalogue foods and immutable nutrition snapshots;
- revision-owned permitted substitutions;
- athlete assignments referencing a template revision and prescription;
- assignment-owned snapshots of prescription targets, food facts, ordering and
  reconciliation/tolerance/override decision at publication;
- append-only override, substitution-selection and adherence event tables.

Use fixed-precision `NUMERIC`, never binary float, for quantities and calculated
macro snapshots. Enforce non-negative macros, positive portions and positions,
allowed lifecycle/day-mode/event values, and uniqueness such as
`(revision_id, position)`, `(day_id, position)` and `(meal_id, item_key)`.
Index every foreign key used for traversal. In particular, assignments need an
athlete/effective-period index; events need `(assignment_id, occurred_at, id)`;
and revision children need parent/position indexes (often satisfied by their
unique constraints).

Assignments for the same athlete and resolution dimension must not overlap.
Define that dimension before DDL: at minimum it is athlete plus day type; if a
plan applies to selected weekdays, persist an explicit schedule key rather than
hiding it in JSON. Use the same PostgreSQL exclusion/locking strategy as macro
prescriptions. Drafts may overlap; enforce exclusion only for resolvable states
(`scheduled`/`active`) with a partial constraint or separate immutable
publication record.

Foreign keys from mutable catalogue/template objects must not make history
mutable. Published assignment snapshots are the durable truth. Use `RESTRICT`
for referenced revisions/snapshots, `SET NULL` for optional actor accounts, and
retain actor/reason snapshots. Athlete/account erasure policy must be explicit:
either controlled cascade for legal deletion or pseudonymization, not accidental
cascade from catalogue cleanup.

## Expand, migrate, contract

1. **Expand macro:** create empty tables, constraints and indexes. Deploy code
   capable of dual-read/fallback, with writes gated. No legacy data changes.
2. **Enable macro writes:** write new coach prescriptions only to the new store;
   continue preserving check-in target snapshots. Read authoritative targets by
   date from prescriptions and fall back to legacy display only when no record
   exists, clearly labelling provenance.
3. **Expand meal plans:** create its empty graph and event tables. Deploy draft
   and publication code gated independently. Publication snapshots the macro
   record; it must never depend on a later mutable join for historical display.
4. **Migrate deliberately:** if product evidence supports it, create reviewed,
   idempotent backfill commands with dry-run counts, provenance and checkpoints.
   Do not put large or inferential data transforms in PreSync DDL.
5. **Retire legacy reads:** measure absence of old writes and fallback reads for
   at least one rollback window, then remove UI writes in a code release.
6. **Contract later:** only a subsequent migration may add `NOT NULL` after
   validation, remove obsolete indexes/columns, or tighten permissions. Legacy
   check-in target columns should remain as historical snapshots unless a
   separately approved retention decision says otherwise.

Nutrition entitlement is checked when creating, scheduling, publishing or
mutating a plan. Revoking entitlement blocks future privileged actions and new
athlete access, but does not delete prescriptions, assignments or audit events.
Historical coach/admin access remains authorization-controlled. A scheduled
future entitlement change must be evaluated at the action/effective time, not
only when the record was drafted.

## Rollback and forward-fix

Both V7.9 upgrades must be transactional where PostgreSQL permits. On a failed
PreSync job, no new application ReplicaSet should roll out; investigate and
rerun after fixing the same revision only if it was never released. Once a
revision has reached a shared environment, migration files are immutable: ship
a new forward-fix revision.

Application rollback after an additive migration is safe: leave the expanded
tables in place and roll back the image/feature flags. Do not automatically run
Alembic downgrade during a Helm rollback. Downgrade is for rehearsal or an
explicit incident procedure before new-table writes exist. After writes begin,
dropping either schema destroys authoritative/audit history; recovery is restore
from backup or forward-fix, not routine downgrade.

Test downgrades on empty and synthetic databases to ensure DDL reversibility,
but document them as destructive. Test upgrade from `0015_client_services`,
upgrade through both revisions, old-image operation against expanded schema,
and a new image with each feature disabled.

## Production PreSync controls

The Helm migration Job is a `pre-install,pre-upgrade` hook (mapped to PreSync by
Argo CD) with weight `-10`, `backoffLimit: 0`, a 600-second deadline, and the
candidate image. It currently runs only `flask db upgrade`; it does not run
`verify-schema`. Therefore:

- render the chart in CI and confirm the migration and Deployment use the same
  immutable image digest, while retaining distinct migration/runtime credentials;
- before promotion, assert one Alembic head and that the candidate head descends
  from the deployed database revision;
- rehearse on a production-shaped sanitized PostgreSQL restore, measuring table
  locks, lock waits, extension creation, index duration, WAL and total runtime;
- set explicit PostgreSQL `lock_timeout` and `statement_timeout` below the Job
  deadline so Kubernetes does not terminate an uncertain in-flight operation;
- avoid `CREATE INDEX CONCURRENTLY` inside Alembic's normal transaction. If scale
  requires it, use a separately reviewed non-transactional operational step and
  make its restart/idempotency behavior explicit;
- add post-upgrade schema/revision validation to the release process before the
  new feature is enabled. The existing verifier checks missing tables/columns
  only, so it does not prove heads, FKs, checks, exclusions or indexes;
- alert on a failed/stuck hook and preserve Job logs before its next run deletes
  the prior Job (`before-hook-creation`). A failed hook is a stopped release,
  not permission to bypass migration ordering.

## Review gates

- exactly one head before and after each revision;
- no edits to previously released migration files;
- generated PostgreSQL DDL reviewed, not only SQLite tests;
- upgrade/downgrade tests plus legacy-row preservation tests;
- concurrent overlap tests proving one of two conflicting writes loses;
- query plans for current-prescription, current-assignment and event-history
  reads with production-like cardinality;
- deletion tests proving catalogue/user cleanup cannot erase published history;
- entitlement revocation and scheduled-change tests;
- PreSync failure, old-image rollback and forward-fix rehearsal with backups.
